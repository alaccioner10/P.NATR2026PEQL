Arquitectura del Proyecto SGE

El sistema implementa una **Arquitectura de Cebolla (Onion Architecture)**, estructurada en cuatro proyectos separados. Esta disposición garantiza la inversión de dependencias: las capas externas dependen de las internas, aislando el núcleo de negocio (Dominio) de cambios en la base de datos o el framework web.

Resumen de las Capas

SGE.Dominio (El Corazón)

Contiene las entidades de negocio (`Expediente`, `Tramite`, `Usuario`), las reglas de dominio que validan estados y propiedades, y excepciones específicas del dominio. Cero dependencias externas o de base de datos.

SGE.Aplicacion (El Director)

Define los Casos de Uso del sistema como clases que orquestan el negocio (ej. `AgregarExpedienteUseCase`). Define interfaces de repositorios (`IExpedienteRepository`) e interfaces de servicios (`IAutorizacionService`). Maneja los DTOs.

SGE.Infraestructura (El Obrero)

Implementa el acceso a datos físico usando Entity Framework Core con SQLite. Implementa los repositorios concretos y los adaptadores de seguridad externos (como el generador de tokens JWT `ProveedorTokenJwt`).

SGE.WebApi (El Mensajero)

Recibe llamadas REST a través de controladores (`ExpedientesController`, `UsuariosController`, `TramitesController`). Configura el contenedor de Dependencias (DI) en `Program.cs` y levanta la consola Swagger.

Capa de Dominio (SGE.Dominio)

El **Núcleo Puro del Negocio**. Contiene los conceptos, reglas y comportamientos esenciales del sistema. Está diseñada para estar aislada del exterior: no tiene dependencias de persistencia (como EF Core) ni de comunicación (como ASP.NET Core). Si las tecnologías externas cambian, el dominio permanece intacto.

Fundamentos de Diseño en el Dominio

Esta capa aplica principios de Diseño Guiado por el Dominio (DDD) para modelar el negocio mediante entidades consistentes y objetos de valor auto-validados. Al encapsular la validación en el constructor de cada objeto, garantizamos que ninguna entidad pueda entrar en un estado inconsistente o inválido (Invariantes del Dominio).

Entidad Principal Expedientes/Expediente.cs

Expediente

public class Expediente

Representa un legajo o carpeta administrativa que agrupa trámites y sigue un ciclo de vida normado por estados.

Explicación Teórica:

En el paradigma de Diseño Guiado por el Dominio (DDD), una entidad se define primordialmente por poseer una identidad conceptual única que persiste a lo largo del tiempo, diferenciándose de los objetos de valor cuya igualdad se mide por sus atributos. `Expediente` actúa en el sistema como la Raíz del Agregado (Aggregate Root). Al ser la raíz, es el único punto de contacto con el exterior para gobernar las entidades internas como los trámites. La teoría de agregados establece que cualquier cambio en los elementos dependientes debe coordinarse a través de la raíz para asegurar que se respeten estrictamente las invariantes lógicas y el estado global del conjunto.

Funcionamiento Interno y Máquina de Estados:

Cada vez que se anexa un trámite al expediente, la entidad evalúa la etiqueta del trámite insertado a través del método de comportamiento `ActualizarEstado()`. La máquina de estados evalúa la transición mediante reglas fijas: la ausencia de trámites coloca al expediente en `RecienIniciado`, la etiqueta `PaseAEstudio` lo lleva al estado `ParaResolver`, la etiqueta `Resolucion` lo actualiza a `ConResolucion` y la etiqueta `PaseAlArchivo` concluye el ciclo de vida marcándolo como `Finalizado`.

Código Clave (SGE.Dominio/Expedientes/Expediente.cs):
// Constructor privado para EF Core private Expediente() { } // Factoría técnica para reconstruir desde la BD public static Expediente Reconstruir(Guid id, Caratula caratula, EstadoExpediente estado, DateTime creacion, DateTime modif, Guid userModif) => new() { Id = id, Caratula = caratula, Estado = estado, FechaCreacion = creacion, FechaUltimaModificacion = modif, UsuarioUltimoCambio = userModif }; // Máquina de estados encapsulada public bool ActualizarEstado(EtiquetaTramite? ultEtiqueta, Guid idUser) { EstadoExpediente estadoAntes = Estado; switch (ultEtiqueta) { case EtiquetaTramite.PaseAEstudio: Estado = EstadoExpediente.ParaResolver; break; case EtiquetaTramite.Resolucion: Estado = EstadoExpediente.ConResolucion; break; case EtiquetaTramite.PaseAlArchivo: Estado = EstadoExpediente.Finalizado; break; } RegistrarModificacion(idUser); return estadoAntes != Estado; }

Análisis del código: El constructor privado sin parámetros le permite a Entity Framework Core omitir el flujo de validación regular y la marca de fecha actual al recuperar expedientes desde SQLite. En su lugar, el método factory `Reconstruir` mapea de forma atómica los valores históricos del disco. La actualización de estados se encapsula estrictamente en `ActualizarEstado`, asegurando la coherencia lógica interna.

Entidad Tramites/Tramite.cs

Trámite

public class Tramite

Representa un documento, providencia o actuación formal anexada a un expediente para justificar un paso administrativo.

Explicación Teórica:

Conceptualmente, un trámite representa una entidad interna subordinada dentro del agregado `Expediente`. Aunque cuenta con su propio identificador único para permitir búsquedas y mapeo relacional en la base de datos, carece de significado de existencia o independencia fuera de su relación de pertenencia con un legajo administrativo específico. Esto modela una relación rígida de composición, donde la vida útil del trámite está ligada indisolublemente a la de su expediente padre.

Funcionamiento Interno:

Su creación requiere un enlace lógico obligatorio a través del atributo `ExpedienteId`. La modificación del trámite no ocurre por edición directa de campos, sino que está encapsulada en el método `ModificarContenido()`. Al invocar este método, se valida el nuevo contenido provisto y de forma automática se actualiza la marca de tiempo de última modificación y se deja registro del usuario que efectuó la operación, garantizando una traza de auditoría robusta y confiable de todos los movimientos.

  • Propiedades: `Id`, `ExpedienteId` (FK lógica), `Etiqueta` (EtiquetaTramite), `Contenido` (Value Object), `FechaCreacion`, `FechaUltModificacion` y `UsuarioUltCambio`.
Entidad Usuarios/Usuario.cs

Usuario

public class Usuario

Modela a los agentes del sistema que operan sobre los expedientes y trámites.

Explicación Teórica:

El usuario es la entidad que representa al sujeto activo dentro de las políticas de seguridad de la aplicación. En el ámbito del diseño de seguridad, se encarga de portar las credenciales básicas y las reclamaciones de privilegios. En lugar de limitarse a un control de accesos basado en roles genéricos (RBAC), el dominio modela permisos granulares basados en acciones atómicas (por ejemplo, el permiso `ExpedienteAlta`), permitiendo implementar autorizaciones robustas y configurables para cada agente en particular.

Funcionamiento Interno:

Almacena la contraseña del usuario hasheada para evitar brechas de seguridad. Posee una bandera lógica `EsAdmin` que introduce una lógica de bypass de seguridad: si un usuario tiene esta propiedad en verdadero, los servicios de validación de seguridad cortocircuitan de inmediato el chequeo y retornan acceso total implícito sin evaluar la colección de permisos individuales. Al igual que otras entidades, implementa un método estático de factoría `Reconstruir` que facilita la instanciación de usuarios desde persistencia sin afectar las auditorías de creación del sistema.

  • Propiedades: `Id`, `Nombre`, `Email`, `ContrasenaHash`, `EsAdmin` (booleano) y `Permisos` (colección de Enums).
Value Object Expedientes/Caratula.cs

Carátula

public record class Caratula

Combate el antipatrón de Obsesión por Primitivos. Evita tratar el título del expediente como un simple `string` genérico.

Explicación Teórica:

La carátula de un expediente no es una simple cadena de caracteres sin estructura; posee semántica y reglas comerciales claras. En DDD, los objetos de valor (Value Objects) encapsulan estas propiedades. Carecen de identidad conceptual y son totalmente inmutables. Su igualdad con otro objeto similar se dirime por la equivalencia de su contenido de datos y no por referencias en memoria. Ayudan a centralizar la validación, impidiendo que datos primitivos crudos se dispersen por el sistema.

Funcionamiento Interno:

El constructor de este `record class` valida estrictamente los datos ingresados: si recibe una cadena nula, vacía o con puros espacios en blanco, detiene la ejecución arrojando un `DomainException`. De lo contrario, limpia el texto de espacios indeseados al inicio y al final empleando el método `.Trim()` y almacena el resultado. Al ser inmutable, el valor no puede modificarse tras su creación; cualquier actualización requiere instanciar una carátula completamente nueva.

Código Clave (SGE.Dominio/Expedientes/Caratula.cs):
public record class Caratula { public string Valor { get; } public Caratula(string valor) { if (string.IsNullOrWhiteSpace(valor)) throw new DomainException("La carátula no puede estar vacía."); Valor = valor.Trim(); } }

Análisis del código: Al lanzar `DomainException` en el constructor, se imposibilita la existencia de un objeto `Caratula` en estado inválido (en blanco). La palabra clave `record` asegura además semántica de comparación por valor en lugar de comparación por referencia.

Value Object Tramites/Contenido.cs

Contenido

public record class Contenido

Encapsula el cuerpo descriptivo de un trámite.

Explicación Teórica:

Al igual que la carátula del expediente, el contenido de un trámite no debe tratarse de forma genérica como un simple tipo primitivo `string`. El objeto de valor `Contenido` garantiza que ninguna actuación administrativa en el sistema carezca de descripción formal, protegiendo las bases del sistema contra la inconsistencia y la corrupción de datos históricos por vaciado de texto.

Funcionamiento Interno:

En su constructor, evalúa de forma obligatoria que el texto provisto no sea nulo ni vacío. Sobreescribe de manera explícita el método `.ToString()` para que devuelva directamente la propiedad `Valor`, permitiendo que otros módulos y serializadores lean el string limpio de forma natural y directa sin necesidad de invocar propiedades secundarias.

Excepción Excepciones/DomainException.cs

DomainException

public class DomainException : Exception

Explicación Teórica:

Representa el mecanismo de defensa interno del núcleo de negocio. La teoría de diseño de software dicta que el dominio debe proteger sus propias reglas de negocio e invariantes de forma activa y autónoma, sin delegar estas comprobaciones críticas en capas externas como la base de datos o las vistas de usuario.

Funcionamiento Interno:

Esta clase hereda de `Exception` y es lanzada inmediatamente cuando un constructor o método de dominio detecta datos inválidos. Interrumpe el flujo normal de ejecución del hilo de ASP.NET Core, forzando un retorno controlado que luego es atrapado por los controladores de la capa de API Web para transformarlo en una respuesta semántica comprensible para el cliente.

Enumeraciones Clave y sus Significados de Negocio

EstadoExpediente

Establece en qué fase administrativa está el legajo:

  • RecienIniciado: Creado, sin trámites sustanciales evaluados.
  • ParaResolver: Con trámites en estudio; listo para dictamen.
  • ConResolucion: Ya cuenta con una resolución o fallo formal.
  • EnNotificacion: La resolución se está comunicando a las partes.
  • Finalizado: El expediente ha concluido y fue enviado al archivo.

EtiquetaTramite

Tipo formal del trámite ingresado al expediente:

  • EscritoPresentado: Escrito inicial de peticiones.
  • PaseAEstudio: Envío a oficinas técnicas para su análisis.
  • Despacho: Actos administrativos internos de rutina.
  • Resolucion: Dictamen formal que concluye el reclamo.
  • Notificacion: Cédula o aviso a los interesados del legajo.
  • PaseAlArchivo: Orden de guarda física del expediente.

Permiso de Usuario

Acciones atómicas controladas por los Casos de Uso:

  • ExpedienteAlta / Baja / Modificacion: Control total sobre la creación, borrado y edición de caratula/estado de expedientes.
  • TramiteAlta / Baja / Modificacion: Control sobre la incorporación de actuaciones e históricos dentro del legajo.

Capa de Aplicación (SGE.Aplicacion)

La **Orquestadora del Sistema**. Aquí residen los Casos de Uso (Use Cases) que implementan los flujos de negocio del software. Es puramente lógica: recibe DTOs estructurados, consulta datos lógicos mediante interfaces y ejecuta las reglas sobre las entidades de dominio.

Inversión de Dependencias (DIP) en Aplicación

La Capa de Aplicación define los contratos lógicos (interfaces) de cómo se deben guardar o buscar datos y cómo se deben emitir tokens de seguridad. La aplicación no sabe cómo conectarse a SQLite o a una base de datos Oracle; solo exige un objeto que cumpla con `IExpedienteRepository`. La capa de **Infraestructura** será la encargada de implementar estas interfaces más tarde.

Orquestadores Expedientes/UseCases/

Casos de Uso (Expedientes)

Implementaciones de Single Responsibility Principle (SRP) para el ciclo de vida del legajo.

Explicación Teórica:

Representan los coordinadores de flujo de la aplicación. Siguiendo el principio de responsabilidad única (SRP), cada caso de uso se dedica a resolver un único requerimiento de negocio de cara al usuario final. La teoría indica que estas clases no deben contener lógica del negocio pura (reglas intrínsecas del expediente), sino dedicarse exclusivamente a orquestar la obtención de datos, mandar comandos al dominio y persistir el resultado de forma atómica.

Funcionamiento Interno:

Al recibir un DTO plano desde la Web API, cada interactor invoca en primera instancia al `IAutorizacionService` para verificar los privilegios del usuario solicitante. Por ejemplo, `AgregarExpedienteUseCase` requiere el permiso `ExpedienteAlta`. Si la verificación es aprobada, transforma la entrada de texto en un Value Object `Caratula`, instancia la entidad `Expediente`, invoca la inserción en el `IExpedienteRepository` y finalmente confirma el guardado mediante la Unidad de Trabajo (`IUnidadDeTrabajo.Guardar()`).

Orquestadores Tramites/UseCases/

Casos de Uso (Trámites)

Gestionan el flujo de las actuaciones administrativas.

Explicación Teórica:

Los casos de uso de trámites actúan de puente para coordinar la mutación de estado que ocurre en el expediente a partir de la inyección de actuaciones particulares. Al alterar de forma separada los trámites del expediente raíz, estas clases coordinan la interacción de múltiples repositorios y servicios internos para evitar estados parciales e inconsistentes.

Funcionamiento Interno:

En `AgregarTramiteUseCase`, tras validar la tenencia del permiso `TramiteAlta`, el interactor consulta en el repositorio el expediente de destino. Crea un nuevo objeto de dominio `Tramite` y actualiza el estado del expediente padre llamando a su método correspondiente. Finalmente, se persiste todo en base de datos de manera atómica.

Código Clave (SGE.Aplicacion/Tramites/UseCases/AgregarTramiteUseCase.cs):
public class AgregarTramiteUseCase( IExpedienteRepository expRepo, ITramiteRepository tramRepo, IAutorizacionService authService, IUnidadDeTrabajo uow) { public void Ejecutar(Guid usuarioId, Guid expedienteId, TramiteDTO dto) { if (!authService.PoseePermiso(usuarioId, Permiso.TramiteAlta)) throw new AutorizacionException("Acceso denegado."); var exp = expRepo.ObtenerPorId(expedienteId) ?? throw new AplicationException("Expediente no encontrado."); var tramite = new Tramite(expedienteId, dto.Contenido, dto.Etiqueta, usuarioId); tramRepo.Agregar(tramite); exp.ActualizarEstado(dto.Etiqueta, usuarioId); expRepo.Modificar(exp); uow.Guardar(); } }

Análisis del código: Este caso de uso orquesta la lógica transaccional. Utiliza el constructor C# 12 (*Primary Constructors*) para inyectar las dependencias abstractas del sistema, lo que mantiene la capa desacoplada de la base de datos o frameworks concretos de seguridad.

Orquestadores Usuarios/UseCases/

Casos de Uso (Usuarios)

Administran el ingreso y registro de agentes.

Explicación Teórica:

Estos casos de uso gobiernan los límites de acceso al sistema, administrando el flujo de creación de agentes y la validación de contraseñas bajo estándares criptográficos y esquemas de tokens web de seguridad.

Funcionamiento Interno:

En el registro, se chequea a través del `IUsuarioRepository` si el correo ingresado está libre de uso. Si no está registrado, hashea la contraseña usando el algoritmo SHA-256 a través del helper `ContrasenaUtil` y crea la entidad. En el inicio de sesión (`LoginUseCase`), busca al usuario por email, aplica la función de hash a la contraseña provista por el cliente y la compara con la registrada. Si coinciden, solicita al `ITokenProvider` la generación de la firma digital JWT que se enviará en formato string de vuelta al frontend.

Contratos (DIP) Contratos/

Interfaces y Contratos

Definen las operaciones que la aplicación requiere del exterior.

Explicación Teórica:

El principio de Inversión de Dependencias (DIP) sostiene que las capas de alto nivel (como la Aplicación) no deben depender de los detalles de bajo nivel (como las bases de datos o servicios externos), sino de abstracciones. Al declarar las interfaces de repositorios en el núcleo de la aplicación, este define las reglas del juego de forma aislada. La capa de infraestructura física se adaptará a estas interfaces, garantizando el total desacoplamiento tecnológico.

Funcionamiento Interno:

La aplicación interactúa directamente con `IExpedienteRepository` o `ITramiteRepository` bajo la suposición lógica de que se trata de colecciones en memoria. En tiempo de ejecución, el contenedor de servicios de ASP.NET Core inyecta dinámicamente las clases concretas de la capa de Infraestructura que se conectan a SQLite de forma totalmente transparente para el caso de uso.

Servicios Co-orquestadores Servicios/

Servicios de Aplicación

Lógica de orquestación que cruza múltiples entidades.

Explicación Teórica:

Un servicio de aplicación encapsula lógica o reglas de coordinación que exceden la competencia de una entidad única del dominio. Se encargan de enlazar flujos de múltiples agregados para simplificar las llamadas dentro de los interactores y mantener limpias las clases principales.

Funcionamiento Interno:

`AutorizacionService` consulta el `IUsuarioRepository` cargando al usuario activo; si el flag `EsAdmin` está activo aprueba la llamada, de lo contrario verifica si la lista de permisos contiene el permiso granular solicitado y arroja un `AutorizacionException` si falla. Por otra parte, `ActualizadorEstadoExpedienteService` se ejecuta para recalcular el estado del legajo padre a partir de la etiqueta del último trámite guardado, modificando la entidad de forma directa.

Mensajeros DTOs/

Data Transfer Objects

Estructuras de datos planas (`record class`) usadas para ingresar y retornar información en los Casos de Uso.

Explicación Teórica:

Los DTOs sirven para desacoplar el modelo del dominio (las clases con lógica interna) del modelo de comunicación externo (JSONs del cliente). Esto impide que cambios estéticos en la API afecten las reglas del dominio y protege al sistema de ataques de asignación masiva (Overposting) al ignorar campos no autorizados de forma directa.

Funcionamiento Interno:

Son modelados en C# como `record class`, favoreciendo la inmutabilidad y la ligereza. ASP.NET Core deserializa automáticamente los JSONs HTTP a estas clases planas y los inyecta en los parámetros de los métodos del caso de uso. Al finalizar el flujo, se mapean nuevamente las propiedades del dominio de interés público en DTOs de salida para retornar respuestas limpias de referencias circulares.

Capa de Infraestructura (SGE.Infraestructura)

El **Proveedor de Detalles Técnicos**. En esta capa se programan los accesos reales al disco rígido, base de datos SQLite, cifrado de claves, y validaciones de tokens JWT. Implementa las interfaces definidas en la Capa de Aplicación.

Implementaciones de Persistencia y Driver SQLite

La base de datos elegida es **SQLite** (a través del driver ligero local `SGE.db`). La infraestructura configura Entity Framework Core para traducir las operaciones orientadas a objetos C# en comandos nativos SQL sin arrastrar dependencias de persistencia al Dominio.

Contexto DB Context SGEContext.cs

SGEContext

public class SGEContext : DbContext

Configuración y mapeo de tablas mediante EF Core.

Explicación Teórica:

El DbContext de Entity Framework Core representa el mapeador objeto-relacional (ORM) oficial de la aplicación. Su función es servir de traductor inteligente para que las entidades complejas de C# puedan almacenarse sin esfuerzo en tablas relacionales SQL ordinarias, absorbiendo los detalles de persistencia y previniendo que la estructura relacional interfiera con el modelo limpio del dominio.

Funcionamiento Interno:

Usa Fluent API para declarar las reglas de mapeo físico. Debido a que SQLite no tiene soporte nativo para los tipos lógicos inmutables del dominio (`Caratula` y `Contenido`), configura convertidores de tipo transparentes (`HasConversion()`) para serializar estos records a strings planos al guardar, y reconstruirlos al realizar lecturas. Adicionalmente, implementa el semillado de base de datos (`OnModelCreating`) insertando los tres usuarios de prueba iniciales del sistema.

Código Clave (SGE.Infraestructura/SGEContext.cs):
protected override void OnModelCreating(ModelBuilder modelBuilder) { // Mapeo y conversión del Value Object modelBuilder.Entity(entity => { entity.Property(e => e.Caratula) .HasConversion( c => c.Valor, v => new Caratula(v) ); }); // Carga de Semilla de Datos Inicial modelBuilder.Entity().HasData( new Usuario("admin@sge.com", "admin123", true) { Id = Guid.Parse("11111111-1111-1111-1111-111111111111") } ); }

Análisis del código: El método `HasConversion` actúa como un puente bidireccional. Permite almacenar la carátula como una columna `TEXT` de SQL y reconstruirla automáticamente con validaciones cuando EF Core recupera la entidad, salvando la impedancia de objeto-relacional.

Persistencia Concreta Repositorios/

Repositorios de Datos

Implementan los contratos de la aplicación inyectando el `SGEContext`.

Explicación Teórica:

Los repositorios concretos representan adaptadores secundarios dentro de la arquitectura de puertos y adaptadores. Su función exclusiva es implementar el contrato lógico declarado por la aplicación y ejecutar comandos de persistencia utilizando la herramienta técnica en curso (en este caso, EF Core consultando a SQLite).

Funcionamiento Interno:

Cada clase accede al DbContext compartido por la petición. Ejecutan llamadas directas a las colecciones (`_context.Expedientes` o `_context.Tramites`). En el caso de eliminaciones, comprueban primero la existencia física del ID en base de datos; si la entidad no es encontrada, lanzan un error controlado de tipo `RepositoryException` en vez de permitir un fallo fatal e inesperado a nivel del motor de base de datos.

Diseño Transaccional UnidadDeTrabajo.cs

Unidad de Trabajo

public class UnidadDeTrabajo : IUnidadDeTrabajo

Implementa el patrón de diseño **Unit of Work**.

Explicación Teórica:

El patrón de diseño Unidad de Trabajo coordina las operaciones de escritura en base de datos. Asegura que múltiples operaciones CRUD llevadas a cabo por repositorios distintos a lo largo de un caso de uso se consoliden en una única transacción atómica a nivel relacional, evitando guardados parciales e inconsistencias físicas de datos si una operación intermedia llega a fallar.

Funcionamiento Interno:

Envuelve la llamada al método `SaveChanges()` del DbContext compartido. Dado que EF Core implementa implícitamente transacciones atómicas al llamar a `SaveChanges()`, la Unidad de Trabajo consolida todos los cambios registrados por los repositorios en el scope de la petición actual en un único bloque transaccional sobre SQLite.

Seguridad y Cifrado Servicios/ProveedorTokenJwt.cs

ProveedorTokenJwt

public class ProveedorTokenJwt : ITokenProvider

Generador físico de cadenas JWT firmadas para autenticar a los clientes.

Explicación Teórica:

La autenticación sin estado (stateless) mediante JSON Web Tokens (JWT) permite que el servidor valide la identidad y permisos de un cliente sin almacenar sesiones en base de datos. Toda la información de identidad e inspección de privilegios es empaquetada y cifrada de forma segura dentro del payload del token.

Funcionamiento Interno:

Inyecta la clave secreta provista por configuración. El método `GenerarToken()` recibe el objeto `Usuario` y construye los reclamos (Claims) lógicos. Si no es admin, incorpora un claim de tipo `"permiso"` por cada uno. Firma digitalmente usando el algoritmo simétrico HMAC-SHA256 y omite el campo de vencimiento para facilitar las pruebas locales.

Código Clave (SGE.Infraestructura/Servicios/ProveedorTokenJwt.cs):
public string CrearToken(Usuario usuario, List permisos) { var claims = new List { new Claim(ClaimTypes.Name, usuario.Email), new Claim(ClaimTypes.NameIdentifier, usuario.Id.ToString()) }; // Inyección de reclamos de permisos claims.AddRange(permisos.Select(p => new Claim("permiso", p.ToString()))); var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_secretKey)); var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256); var token = new JwtSecurityToken( claims: claims, signingCredentials: creds ); return new JwtSecurityTokenHandler().WriteToken(token); }

Análisis del código: Los permisos granulares son mapeados como múltiples reclamos atómicos de tipo `permiso` en el JWT. El cliente (API Web) descodifica este token y valida si el array de claims contiene el permiso requerido por el endpoint.

Manejo de Excepciones Mapeo HTTP

Mapeo de Errores a Códigos HTTP

Los controladores encierran las llamadas en bloques `try-catch` para traducir excepciones lógicas a códigos estándar de la web.

Explicación Teórica:

En una API RESTful, las excepciones de código internas (como excepciones por punteros nulos o fallos lógicos crudos) nunca deben exponerse al exterior, por motivos de seguridad y de conformidad con el protocolo HTTP. Los controladores o middlewares de soporte se encargan de capturar de forma ordenada estos incidentes lógicos y mapearlos a respuestas HTTP estructuradas con códigos de estado semánticos predefinidos por la especificación RFC del protocolo.

Funcionamiento Interno:

A través de un bloque `try-catch` en cada endpoint de los controladores, se captura de manera selectiva la clase de excepción levantada y se traduce a un código HTTP semántico. Cualquier otro error no controlado del sistema retorna un código genérico `500 Internal Server Error`, manteniendo ocultos los detalles técnicos sensibles de la infraestructura.

Código Clave (Ejemplo de Mapeo en Controladores):
[HttpPost] public IActionResult Agregar([FromBody] TramiteRequest request) { try { var userId = ObtenerUsuarioIdDeClaims(); _agregarTramiteUseCase.Ejecutar(userId, request.ExpedienteId, request.ToDto()); return Ok(); } catch (AplicationException ex) { return BadRequest(new { mensaje = ex.Message }); // 400 Bad Request } catch (AutorizacionException ex) { return StatusCode(403, new { mensaje = ex.Message }); // 403 Forbidden } catch (Exception ex) { return StatusCode(500, new { mensaje = "Ocurrió un error inesperado." }); // 500 } }

Análisis del código: La captura selectiva de excepciones evita que la capa Web API acople su protocolo a las excepciones internas. Mapea la lógica del negocio (`AplicationException` / `AutorizacionException`) a códigos estándares REST (`400` y `403`), protegiendo el stack trace de errores inesperados (`500`).

Excepción Código HTTP Significado
AplicationException 400 Bad Request Datos inválidos o inconsistencia lógica.
AutorizacionException (Login) 401 Unauthorized Credenciales incorrectas al autenticarse.
AutorizacionException (Permiso) 403 Forbidden El token es válido pero no posee el permiso atómico.
Exception General 500 Internal Error Errores no controlados del servidor.

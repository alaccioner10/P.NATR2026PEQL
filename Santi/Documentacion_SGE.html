0. Cómo Estudiar el Proyecto y Entender la Ingeniería del Trabajo

Este documento no está pensado como manual para un usuario final. La idea es que les sirva al grupo para repasar qué hace cada archivo, por qué existe, cómo se conecta con el resto y qué decisión de diseño lo justifica, aunque el código haya sido escrito por personas distintas.

Idea central para estudiar el proyecto

Si quieren ubicar rápido cualquier clase, conviene preguntarse primero qué problema resuelve y después dónde vive. En este proyecto la lógica se divide en capas: la Presentación recibe pedidos HTTP, la Aplicación coordina acciones, el Dominio guarda las reglas del negocio y la Infraestructura resuelve persistencia, seguridad y detalles técnicos.

Esa separación no es decorativa: permite que cada integrante trabaje sobre una parte concreta del sistema sin romper el resto. Y también ayuda mucho en la defensa, porque cada archivo tiene una razón de ser clara dentro de la arquitectura.

0.2 Flujo mental para seguir cualquier caso de uso

  1. El cliente llama un endpoint de la Web API.
  2. El controlador recibe el DTO y, si hace falta, toma el usuario autenticado del token.
  3. El caso de uso chequea permisos y convierte lo que llega en objetos de dominio.
  4. El dominio valida las reglas que no se pueden romper.
  5. La infraestructura guarda los cambios y se encarga de SQLite.
  6. El caso de uso arma la respuesta y el controlador devuelve HTTP.

Si entienden ese recorrido, el resto del código deja de verse como archivos sueltos y pasa a leerse como una cadena de responsabilidades que encaja. Esa cadena es útil para estudiar porque permite seguir el camino de un dato desde que entra al sistema hasta que termina guardado o devuelto al cliente.

0.3 Qué hace cada módulo y por qué está separado

En esta parte conviene mirar el proyecto como si cada módulo fuera una pieza distinta de un mismo mecanismo. Algunos se ocupan de las reglas, otros de la coordinación y otros de la tecnología. Esa separación evita mezclar todo en un único archivo y hace que el trabajo se pueda repartir y entender mejor.

Módulo Qué hace Por qué está en su propia capa o carpeta
SGE.Dominio Modela el negocio puro: expedientes, trámites, usuarios, permisos, estados y reglas de validación. Acá están las decisiones que no deberían cambiar aunque cambie la base de datos o la interfaz. Se aísla para que las reglas del negocio no dependan de SQLite, JWT ni de la Web API. Si mañana cambia la tecnología, el dominio debería seguir igual.
SGE.Aplicacion - General Contiene interfaces y servicios transversales como autorización, unidad de trabajo y manejo de excepciones de aplicación. Es el soporte que usan varios módulos sin repetir código. Separa las necesidades comunes del negocio para que los casos de uso no repitan lógica técnica y para que las dependencias queden ordenadas.
SGE.Aplicacion - Expedientes Coordina altas, consultas, modificaciones, cambios de estado y eliminaciones de expedientes. Acá se ve el ciclo de vida completo del expediente desde que nace hasta que cambia de estado o se elimina. Agrupa todo lo relacionado con el expediente para que el flujo sea fácil de seguir y para que no quede repartido entre varias carpetas.
SGE.Aplicacion - Trámites Orquesta la creación, edición, consulta, listado y baja de trámites asociados a un expediente. También conecta el alta del trámite con el cambio de estado del expediente cuando corresponde. Se separa porque el trámite no se maneja igual que un expediente y tiene sus propias reglas, etiquetas y efectos sobre el agregado principal.
SGE.Aplicacion - Usuarios Gestiona registro, login, modificación de datos, permisos y consulta/eliminación de usuarios. Es uno de los módulos más sensibles porque de acá depende quién puede hacer qué dentro del sistema. Se aísla porque la seguridad y la identidad del usuario afectan a toda la aplicación y conviene tenerlo claramente separado del resto del negocio.
SGE.Infraestructura Implementa la persistencia en SQLite, los repositorios, la autenticación JWT y la coordinación física de datos. También traduce las entidades del dominio a estructuras guardables en base. Porque son detalles técnicos que pueden cambiar sin alterar el corazón del negocio. Así el dominio y la aplicación no quedan atados a una tecnología específica.
SGE.WebApi Expone los controladores HTTP, configura Swagger, el middleware, la autenticación y el arranque de la aplicación. Es la cara pública del sistema y el punto por donde entra todo lo externo. Es la frontera de entrada del sistema; traduce las peticiones externas al lenguaje de la aplicación y decide cómo presentar la respuesta.

1. Flujo General de Ejecución del Sistema

El sistema funciona bajo el principio de arquitectura por capas desacoplada. Una petición viaja de la siguiente manera:

Diagramas de Secuencia y Flujos de Datos

Para facilitar el seguimiento del flujo de la información, a continuación se detallan los diagramas de secuencia interactivos de las operaciones críticas del sistema, ilustrando cómo se comunican las distintas capas (Presentación, Aplicación, Dominio e Infraestructura) a medida que viajan los datos.

Flujo 1: Registro de un Nuevo Usuario

Muestra el camino de los datos cuando un administrador crea un nuevo usuario en el sistema. Los datos pasan del controlador al caso de uso, se hashea la contraseña de forma unidireccional y se persiste en SQLite.

Flujo 2: Inicio de Sesión (Login)

Muestra el flujo de credenciales para obtener un token JWT firmado. La API valida contra SQLite la existencia del usuario, verifica el hash de la contraseña y genera el JWT.

Flujo 3: Creación de un Expediente

Muestra el flujo al dar de alta un expediente. Requiere cabecera JWT válida. El caso de uso evalúa permisos, crea la raíz de agregado y lo guarda de forma segura.

Flujo 4: Consulta de un Expediente y sus Trámites

Muestra el flujo de lectura de datos. EF Core lee la base de datos relacional, convierte los Value Objects primitivos a objetos ricos y retorna un DTO seguro estructurado.

Flujo 5: Anexar un Trámite a un Expediente

Muestra el flujo completo cuando se agrega un trámite. Involucra la máquina de estados del Expediente (para cambiar a Finalizado si es PaseAlArchivo) y la persistencia atómica coordinada por la Unidad de Trabajo.

2. Detalle de Clases: Capa de Dominio (SGE.Dominio)

Representa el núcleo puro del negocio. Contiene las entidades principales, que encapsulan estado y reglas de negocio, y los Value Objects (Objetos de Valor).

Fundamentos Teóricos del Diseño Guiado por el Dominio (DDD)

La capa de Dominio es el corazón de la aplicación. Representa los conceptos, las reglas del negocio y los casos de lógica pura que definen el comportamiento de nuestro sistema. De acuerdo con los principios del Domain-Driven Design (DDD), esta capa no tiene dependencias de ningún elemento externo (como bases de datos, APIs o frameworks), lo que garantiza su portabilidad y estabilidad ante cambios técnicos. Sus componentes clave se dividen en:

1. Entidades y Raíces de Agregación (Aggregate Roots): Una Entidad es un objeto que posee una identidad única que trasciende el tiempo y los cambios de estado (representada por un ID único de tipo Guid). El Agregado es un conjunto de entidades y objetos de valor que se tratan como una única transacción lógica. La raíz del agregado (Aggregate Root), como la clase Expediente, es el único punto de contacto con el exterior del agregado. Cualquier cambio en sus partes internas (como añadir un Tramite o modificar una fecha de actualización) debe realizarse obligatoriamente a través de métodos expuestos en la raíz. Esto previene que los objetos queden en estados corruptos o inconsistentes.

2. Objetos de Valor (Value Objects): A diferencia de las entidades, los Value Objects carecen de una identidad conceptual propia. Se definen únicamente por sus propiedades (como Caratula o Contenido) y son inmutables: si un objeto de valor cambia, se reemplaza por uno completamente nuevo en lugar de mutar sus propiedades en memoria. La comparación entre dos objetos de valor se hace por igualdad estructural (sus valores internos son idénticos) y no por referencia de puntero, lo que simplifica enormemente la lógica de control.

3. Preservación de Invariantes y Excepciones: Una invariante es una regla de negocio que debe cumplirse en todo momento (por ejemplo, "un expediente finalizado no puede volver a cambiar de estado"). En DDD, las entidades y objetos de valor son responsables de auto-validarse. El constructor y los métodos de negocio evalúan las invariantes preventivamente y lanzan excepciones especializadas (DomainException) si se detecta una anomalía. De este modo, se garantiza que el dominio actúe como un escudo protector, imposibilitando que datos corruptos viajen hacia las bases de datos.

Clase: Expediente.cs

Esta entidad representa un expediente administrativo en el sistema. Es la raíz de agregación y gestiona la coherencia y estados lógicos del expediente. 

namespace SGE.Dominio.Expedientes;

public class Expediente
{
    public Guid Id { get; private set; }
    public DateTime FechaCreacion { get; private set; }
    public DateTime FechaUltimaModificacion { get; private set; }
    public Guid UsuarioUltimoCambio { get; private set; }
    public Caratula Caratula { get; private set; }
    public EstadoExpediente Estado { get; private set; }

    private Expediente()
    {
        Caratula = null!;
    }

    public Expediente(Caratula caratula, Guid user)
        : this(Guid.NewGuid(), DateTime.Now, DateTime.Now, user, caratula, EstadoExpediente.RecienIniciado)
    {
    }

    private Expediente(Guid id, DateTime fechaCreacion, DateTime fechaUltimaModificacion, Guid usuarioUltimoCambio, Caratula caratula, EstadoExpediente estado)
    {
        if (id == Guid.Empty)
        {
            throw new DomainException("El Id no puede ser vacío.");
        }

        if (fechaUltimaModificacion.CompareTo(fechaCreacion) < 0)
        {
            throw new DomainException("La fecha de modificación no puede ser previa a la de creación.");
        }

        Id = id;
        FechaCreacion = fechaCreacion;
        FechaUltimaModificacion = fechaUltimaModificacion;
        UsuarioUltimoCambio = usuarioUltimoCambio;
        Caratula = caratula;
        Estado = estado;
    }

    public static Expediente Reconstruir(Guid id, DateTime fechaCreacion, DateTime fechaUltimaModificacion, Guid usuarioUltimoCambio, Caratula caratula, EstadoExpediente estado)
    {
        return new Expediente(id, fechaCreacion, fechaUltimaModificacion, usuarioUltimoCambio, caratula, estado);
    }

    private void RegistrarModificacion(Guid idUser)
    {
        UsuarioUltimoCambio = idUser;
        FechaUltimaModificacion = DateTime.Now;
    }

    public void ModificarCaratula(Caratula nuevaC, Guid idUser)
    {
        Caratula = nuevaC;
        RegistrarModificacion(idUser);
    }

    public bool ActualizarEstado(EtiquetaTramite? ultEtiqueta, Guid idUser)
    {
        EstadoExpediente estadoAntes = Estado;
        switch (ultEtiqueta)
        {
            case null:
                Estado = EstadoExpediente.RecienIniciado;
                break;
            case EtiquetaTramite.Resolucion:
                Estado = EstadoExpediente.ConResolucion;
                break;
            case EtiquetaTramite.PaseAEstudio:
                Estado = EstadoExpediente.ParaResolver;
                break;
            case EtiquetaTramite.PaseAlArchivo:
                Estado = EstadoExpediente.Finalizado;
                break;
        }

        RegistrarModificacion(idUser);
        return estadoAntes != Estado;
    }

    public bool ActualizarEstado(EstadoExpediente nuevoEstado, Guid idUser)
    {
        EstadoExpediente estadoAntes = Estado;
        Estado = nuevoEstado;
        RegistrarModificacion(idUser);
        return estadoAntes != Estado;
    }
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Definir Expediente como la única Raíz de Agregado (Aggregate Root) que encapsula su propia máquina de estados (ActualizarEstado), restringiendo los setters como private set y proveyendo un constructor privado sin parámetros para la reconstrucción de EF Core junto a una factoría técnica (Reconstruir).
  • Alternativa Descartada: Tener una clase meramente anémica (sólo propiedades públicas con `get; set;` sin métodos de negocio) y manejar el cambio de estado y las validaciones de invariantes dentro de los Casos de Uso.
  • ¿Por qué SÍ? (Ventajas de la decisión): Centraliza las invariantes de negocio (como impedir que un expediente con fecha de última modificación previa a la de creación exista) en un único lugar, evitando inconsistencias. Los setters privados obligan a pasar por los métodos del negocio y previenen manipulaciones arbitrarias de auditoría o de estado en capas externas.
  • ¿Por qué NO? (Desventajas/Limitaciones): Aumenta la complejidad del mapeo de EF Core al requerir configuración explícita para propiedades complejas y obligar a definir constructores privados exclusivamente para la persistencia. Además, escribir pruebas unitarias requiere instanciar entidades completas respetando sus invariantes rígidas.
  • Cómo Defenderlo en el Examen Oral: "Diseñamos el Expediente como un Aggregate Root rico para proteger la consistencia de sus invariantes de negocio en el núcleo del dominio. Al declarar setters privados y exponer métodos explícitos como ModificarCaratula o ActualizarEstado, impedimos que la base de datos o la Web API fuercen transiciones inválidas. La alternativa anémica es riesgosa porque dispersa las reglas de negocio en múltiples casos de uso, duplicando lógica y facilitando la corrupción del estado."
Clase: Caratula.cs

Es un Objeto de Valor (Value Object) que representa la carátula o el título identificador de un expediente. 

namespace SGE.Dominio.Expedientes;

public record class Caratula
{
    public string Valor { get; }
    
    public Caratula(string valor)
    {
        if (string.IsNullOrWhiteSpace(valor))
        {
            throw new DomainException("El nombre de la caratula no puede estar vacío.");
        }
        Valor = valor.Trim();
    }

    public override string ToString() => Valor;
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Modelar la carátula como un Objeto de Valor (Value Object) implementado mediante un record class inmutable, con validación de no-vacío y normalización (Trim) en su constructor.
  • Alternativa Descartada: Representar la carátula como una propiedad simple de tipo `string` directamente en la entidad `Expediente` (y validar el texto en el caso de uso o DTO).
  • ¿Por qué SÍ? (Ventajas de la decisión): Centraliza la invariante estructural en el propio tipo de dato; un objeto `Caratula` sólo existe si su estado es coherente. Al usar `record class`, obtenemos comparación de igualdad estructural nativa (por valor en vez de por referencia) sin sobrecargar operadores manualmente.
  • ¿Por qué NO? (Desventajas/Limitaciones): Introduce una clase adicional en el dominio y complejiza el mapeo relacional en EF Core, que debe configurarse explícitamente mediante `.ComplexProperty()` para que la columna en la base de datos siga siendo un string de SQLite.
  • Cómo Defenderlo en el Examen Oral: "Elegimos encapsular la carátula en un Value Object en lugar de un string plano para proteger la validez del dato en el núcleo de nuestro dominio. La carátula no tiene identidad propia (dos expedientes con el mismo título tienen carátulas conceptualmente iguales) e incluye reglas de limpieza como Trim y validaciones contra nulos. Al usar record class logramos inmutabilidad e igualdad de valor nativas, lo que simplifica enormemente el código y la consistencia."

namespace SGE.Dominio.Tramites;

public class Tramite
{

        : this(Guid.NewGuid(), expediente, etiqueta, contenido, DateTime.Now, DateTime.Now, user)
    {
    }

    private Tramite(Guid id, Guid exp, EtiquetaTramite etiqueta, Contenido contenido, DateTime fechaCreacion, DateTime ultModificacion, Guid user)
    {
        if (id == Guid.Empty)
        {
            throw new DomainException("El Id no puede ser vacío.");

        {
            throw new DomainException("La fecha de modificación no puede ser previa a la de creación.");

        ExpedienteId = exp;

        Contenido = contenido;
        FechaCreacion = fechaCreacion;
        FechaUltModificacion = ultModificacion;
        UsuarioUltCambio = user;
    }

    public static Tramite Reconstruir(Guid id, Guid exp, EtiquetaTramite etiqueta, Contenido contenido, DateTime fechaCreacion, DateTime ultModificacion, Guid user)
    {

3. Detalle de Clases: Capa de Aplicación (SGE.Aplicacion)

Esta capa implementa las reglas de orquestación del sistema mediante Casos de Uso, DTOs y validaciones de seguridad específicas.

Fundamentos Teóricos de la Capa de Aplicación

La capa de Aplicación funciona como la orquestadora principal del sistema. Su misión es traducir las intenciones del usuario (recibidas en la API) en acciones de negocio sobre el dominio, coordinando el flujo de datos y controlando la infraestructura técnica mediante interfaces. Sus principios fundamentales son:

1. Casos de Uso (Orquestadores de Flujo): Cada caso de uso (como AgregarExpedienteUseCase o LoginUseCase) representa una operation lógica e individual del negocio. Los casos de uso no contienen las reglas esenciales del negocio (las cuales residen en el dominio), sino que se limitan a cargar entidades desde los repositorios, invocar los métodos comerciales del dominio y llamar al guardado de cambios. De esta forma, el caso de uso es un director de orquesta: dice qué hacer y en qué orden, pero la lógica fina la ejecutan los agregados de dominio.

2. Inversión de Dependencias a través de Puertos (Interfaces): La capa de aplicación no conoce bases de datos, redes o archivos físicos. Define interfaces de acceso (como IExpedienteRepository o IUnidadDeTrabajo) que actúan como "puertos". La capa de Infraestructura implementa estas interfaces (los "adaptadores"). Esto nos permite cambiar el motor de persistencia (por ejemplo, pasar de SQLite a SQL Server o una base de datos Mock para pruebas) sin modificar una sola línea de código en la capa de aplicación o de dominio.

3. Objetos de Transferencia de Datos (DTOs): Representan estructuras de datos planas (records o clases sin lógica) que viajan a través de los límites del sistema. Evitan el acoplamiento directo entre los clientes externos y las entidades de dominio (como Expediente), impidiendo problemas de seguridad (over-posting) y protegiendo el encapsulamiento interno al no exponer propiedades con set privado o relaciones circulares que complicarían la serialización.

public class EliminarExpedienteUseCase
{
    private readonly IUnidadDeTrabajo _uow;
    private readonly IExpedienteRepository _iExpRepo;
    private readonly ITramiteRepository _iTramRepo;
    private readonly IAutorizacionService _autorizacion;

    public EliminarExpedienteUseCase(IUnidadDeTrabajo uow, IExpedienteRepository iExpRepo, ITramiteRepository iTramRepo, IAutorizacionService autorizacion)
    {
        _uow = uow;
        _iExpRepo = iExpRepo;
        _iTramRepo = iTramRepo;
        _autorizacion = autorizacion;
    }

    public EliminarExpedienteResponse Ejecutar(EliminarExpedienteRequest req, Guid idUsuario)
    {
        if (req == null)
        {
            throw new AplicationException("La solicitud no puede estar vacía."); 
        }

        if (!_autorizacion.PoseeElPermiso(idUsuario, Permiso.ExpedienteBaja))
        {
            throw new AutorizacionException("El usuario no tiene permisos para eliminar este expediente.");
        }

        var expedienteABorrar = _iExpRepo.ObtenerPorId(req.ExpedienteId);
        if (expedienteABorrar == null)
        {
            throw new AplicationException("No se encontró el expediente solicitado");
        }

        // Eliminación en Cascada programática a nivel de Aplicación
        var tramites = _iTramRepo.ObtenerPorExpedienteId(req.ExpedienteId).ToList();
        foreach (var t in tramites)
        {
            _iTramRepo.Eliminar(t.Id);
        }

        _iExpRepo.Eliminar(req.ExpedienteId);
        _uow.Guardar();

        return new EliminarExpedienteResponse(req.ExpedienteId);
    }
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Resolver la eliminación en cascada de los trámites asociados al expediente de forma programática y explícita dentro del Caso de Uso (`EliminarExpedienteUseCase`), en lugar de delegarla a la base de datos o al motor de persistencia.
  • Alternativa Descartada: Configurar reglas de eliminación en cascada automáticas (`ON DELETE CASCADE`) en la base de datos SQLite (mediante EF Core o llaves foráneas) y delegar el borrado del expediente directamente.
  • ¿Por qué SÍ? (Ventajas de la decisión): Aporta total portabilidad e independencia de la base de datos (si migramos de SQLite a otro motor que no soporte o tenga restringida la cascada, el código sigue funcionando). Da control absoluto al desarrollador sobre la secuencia, permitiendo disparar eventos de dominio o auditorías para cada trámite borrado.
  • ¿Por qué NO? (Desventajas/Limitaciones): Genera mayor tráfico de red y operaciones en memoria (debemos hacer un `GET` para traer todos los trámites, iterar sobre ellos y ejecutar múltiples sentencias de borrado en memoria que luego viajan en lote a la base de datos).
  • Cómo Defenderlo en el Examen Oral: "Elegimos hacer la eliminación en cascada de forma programática en la capa de Aplicación para mantener nuestra lógica de negocio independiente de las capacidades del motor de base de datos específico (SQLite), respetando la portabilidad. Al traer y borrar cada trámite explícitamente dentro de una única transacción coordinada por la Unidad de Trabajo (Unit of Work), aseguramos que la operación sea atómica: si el borrado de algún trámite falla, la base de datos vuelve a su estado original sin dejar registros huérfanos."

4. Detalle de Clases: Capa de Infraestructura (SGE.Infraestructura)

La capa de infraestructura implementa las interfaces y provee el soporte técnico para las capas internas.

Fundamentos Teóricos de la Capa de Infraestructura

La capa de Infraestructura (implementada en el proyecto SGE.Infraestructura) es la encargada de dar soporte técnico a las reglas lógicas del negocio. Implementa las interfaces (puertos) definidas por las capas internas de Dominio y Aplicación, encargándose de la comunicación física con bases de datos relacionales, servicios de cifrado, archivos del sistema o redes. Sus pilares fundamentales son:

1. Mapeo Relacional de Objetos (ORM) y EF Core: El ORM (en nuestro caso, Entity Framework Core) actúa como un puente de traducción bidireccional entre el paradigma orientado a objetos (clases, herencia, encapsulamiento) y el paradigma relacional de SQL (tablas, columnas, claves foráneas). EF Core nos permite recuperar registros en base de datos e hidratar las clases de negocio automáticamente.

2. Propiedades Complejas (Complex Properties): Dado que los motores relacionales sencillos (como SQLite) no comprenden de forma nativa los Value Objects del dominio (como Caratula o Contenido), la infraestructura utiliza el mapeo de Propiedades Complejas (Complex Properties) de EF Core 8+ para aplanar estos objetos a columnas primitivas en las mismas tablas del expediente y trámite, sin necesidad de IDs adicionales. Esto nos permite mantener un dominio puro y rico sin comprometer la sencillez técnica de la persistencia.

3. Patrones Repositorio y Unidad de Trabajo (Unit of Work): El *Patrón Repositorio* encapsula las consultas y escrituras de datos tras una interfaz en memoria, abstrayendo a la aplicación de los comandos SQL o llamadas al ORM. El *Patrón Unidad de Trabajo* asegura que todas las operaciones y cambios sobre múltiples repositorios ocurran dentro de una transacción de base de datos única y atómica.

4. Servicios de Criptografía e Identidad: Los mecanismos de seguridad (generación de tokens JWT y hashing de contraseñas) se exponen a través de interfaces como IHashService y se implementan concretamente en esta capa para mantener desacoplada la aplicación.

(Ventajas de la decisión): Las propiedades complejas aplanan los Value Objects a columnas simples de la misma tabla padre (`Expedientes` o `Tramites`), optimizando el rendimiento y simplificando el esquema SQL en SQLite.   • Cómo Defenderlo en el Examen Oral: "Diseñamos el DbContext utilizando las propiedades complejas (Complex Types) de EF Core 8+ para mapear los Value Objects de Caratula y Contenido sin necesidad de darles un ID relacional artificial, lo que aplanar los datos en una sola tabla y optimiza SQLite. Inicializador seguro para asegurar la creación del archivo de base de datos SQLite y el impacto de los esquemas iniciales. 

namespace SGE.Infraestructura;

public static class SGESqlite
{
    private static bool _initialized;
    private static readonly object _lock = new();

    public static void Inicializar(SGEContext context)
    {
        if (_initialized)
        {
            return;
        }

        lock (_lock)
        {
            if (_initialized)
            {
                return;
            }

            if (context.Database.EnsureCreated())
            {
                Console.WriteLine("Se creó base de datos");
            }

            _initialized = true;
        }
    }
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Diseñar la inicialización de la base de datos SQLite utilizando el patrón de Bloqueo de Doble Verificación (`Double-Checked Locking`) con una variable estática y un objeto `lock` para asegurar la creación única del archivo físico de SQLite de forma segura entre múltiples hilos.
  • Alternativa Descartada: Ejecutar `EnsureCreated()` directamente en el `Program.cs` sin sincronización de hilos o utilizar migraciones manuales mediante comandos del CLI de dotnet (`dotnet ef database update`).
  • ¿Por qué SÍ? (Ventajas de la decisión): Previene de manera eficiente las condiciones de carrera (Race Conditions) y los bloqueos de archivos en SQLite en entornos web donde múltiples hilos de servidor podrían competir al iniciar la aplicación. Asegura que la verificación rápida inicial (`_initialized`) no requiera bloqueo, ahorrando tiempo de CPU en las peticiones posteriores.
  • ¿Por qué NO? (Desventajas/Limitaciones): `EnsureCreated()` no admite migraciones incrementales. Si modificamos las clases del Dominio en el futuro, no podremos actualizar la base de datos automáticamente; tendremos que eliminar el archivo `.db` existente, lo cual destruirá todos los datos previos.
  • Cómo Defenderlo en el Examen Oral: "Utilizamos el método SGESqlite.Inicializar con bloqueo de doble verificación (Double-Checked Locking) para garantizar que la base de datos SQLite se cree una sola vez de forma thread-safe durante el arranque de la API, impidiendo excepciones por accesos concurrentes. Usamos EnsureCreated en lugar de migraciones complejas porque, dado que es un prototipo escolar y académico, priorizamos la autoejecución automática del esquema sin requerir que el usuario corra comandos de consola previos."

Proveedor de JWT: ProveedorTokenJwt.cs

Se encarga de armar y firmar criptográficamente el token JWT a partir de los datos y permisos de un usuario autenticado. 

public class ProveedorTokenJwt : ITokenProvider
{
    private readonly string _claveSecreta;

    public ProveedorTokenJwt(string claveSecreta)
    {
        _claveSecreta = claveSecreta;
    }

    public string GenerarToken(Usuario user)
    {
        var manejadorToken = new JwtSecurityTokenHandler();
        var claveEnBytes = Encoding.UTF8.GetBytes(_claveSecreta);

        var reclamos = new List<Claim>
        {
            new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
            new Claim(ClaimTypes.Name, user.Nombre),
            new Claim(ClaimTypes.Email, user.Email),
            new Claim("esAdmin", user.EsAdmin.ToString().ToLower())
        };

        if (!user.EsAdmin)
        {
            foreach (var permiso in user.Permisos)
            {
                reclamos.Add(new Claim("permiso", permiso.ToString()));
            }
        }

        var descriptorToken = new SecurityTokenDescriptor
        {
            Subject = new ClaimsIdentity(reclamos),
            SigningCredentials = new SigningCredentials(
                new SymmetricSecurityKey(claveEnBytes),
                SecurityAlgorithms.HmacSha256Signature
            )
        };

        var token = manejadorToken.CreateToken(descriptorToken);
        return manejadorToken.WriteToken(token);
    }
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Diseñar `ProveedorTokenJwt` implementando `ITokenProvider` para generar y firmar digitalmente tokens JWT autónomos conteniendo la identidad y permisos de usuario (`permiso` como claim individual para usuarios no administradores).
  • Alternativa Descartada: Guardar las sesiones de usuario en una base de datos relacional o de clave-valor (como Redis) y entregar una cookie de sesión opaca (`Session Cookies`).
  • ¿Por qué SÍ? (Ventajas de la decisión): Los tokens JWT son completamente autocontenidos y descentralizados (stateless). El servidor no necesita almacenar estados ni consultar la base de datos SQLite para verificar si un token es válido; simplemente valida su firma criptográfica en el middleware, reduciendo la carga y permitiendo escalar la API horizontalmente.
  • ¿Por qué NO? (Desventajas/Limitaciones): Invalidad de tokens compleja: una vez emitido un JWT, es válido hasta que expire. Si revocamos permisos o suspendemos una cuenta, el token del cliente seguirá funcionando a menos que implementemos una lista de tokens revocados (Blacklist) en la base de datos, lo que anularía el beneficio de no guardar estados.
  • Cómo Defenderlo en el Examen Oral: "Elegimos JSON Web Tokens (JWT) para la autenticación y autorización por ser una tecnología stateless e ideal para APIs REST. En lugar de cookies de sesión que requieren almacenamiento persistente en el servidor, el JWT transporta los claims de usuario (id, nombre, email) y su colección de permisos firmados con HMAC SHA-256. Esto permite al middleware de autorización verificar el token y sus permisos de manera inmediata en memoria, agilizando el pipeline HTTP y facilitando la escalabilidad del sistema."

5. Detalle de Clases: Capa de Presentación (SGE.WebApi)

Esta capa expone los controladores REST e implementa el bootstrap de configuración inicial y filtros globales.

Fundamentos Teóricos de ASP.NET Core Web API

La capa de Presentación (implementada en el proyecto SGE.WebApi) constituye la frontera del sistema. Su propósito fundamental es exponer los servicios del negocio al mundo exterior mediante una API web HTTP, actuando como un adaptador de entrada (siguiendo los principios de la Arquitectura Hexagonal y la Arquitectura Limpia). A continuación se analizan sus componentes y mecanismos clave:

1. Arquitectura REST (Representational State Transfer): La Web API está construida sobre los principios de REST, lo que implica una comunicación cliente-servidor sin estado (stateless). Cada petición HTTP debe contener toda la información necesaria para ser procesada. La API utiliza Endpoints basados en URIs que identifican recursos (por ejemplo, /api/expedientes), verbos HTTP estandarizados para denotar intenciones (GET para lectura, POST para creación, PUT/PATCH para modificación y DELETE para eliminación) y códigos de estado HTTP semánticos (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Internal Server Error) para comunicar el resultado de manera uniforme a los clientes.

2. El Bootstrap y el Contenedor de Inversión de Control (IoC): El archivo Program.cs funciona como el punto de entrada de la aplicación (bootstrap). En él se configuran e inicializan los servicios que componen la infraestructura técnica y del negocio. ASP.NET Core incluye un contenedor de dependencias nativo. En la sección de servicios (builder.Services), se registran los componentes del sistema indicando su ciclo de vida (Lifetime):

  • Transient: Se crea una nueva instancia cada vez que se solicita el servicio. Adecuado para componentes livianos y sin estado.
  • Scoped: Se crea una única instancia por cada petición HTTP. Todos los componentes inyectados dentro de una misma solicitud HTTP comparten esta instancia. Es el ciclo de vida crítico para el SGEContext y los Repositorios, ya que asegura que todas las operaciones de acceso a datos de una petición utilicen la misma conexión y sesión relacional.
  • Singleton: Se crea una única instancia para toda la vida útil de la aplicación web. Se comparte entre todas las llamadas HTTP y todos los hilos, siendo ideal para proveedores de cifrado o servicios inmutables de configuración global.

3. El Pipeline de Middleware (Ciclo de Vida de una Petición): El procesamiento de solicitudes en ASP.NET Core se basa en un pipeline de middlewares dispuestos en forma de cebolla. Un Middleware es un componente de software intermedio que intercepta la solicitud y la respuesta. El orden de registro de los middlewares en Program.cs es fundamental porque determina su ejecución secuencial:

  • Middleware de Excepciones: Registrado al principio del pipeline para capturar cualquier error lanzado por middlewares subsecuentes o controladores.
  • Middleware de Autenticación (UseAuthentication): Examina la cabecera HTTP Authorization, valida la firma del token JWT y carga la identidad del usuario en el contexto de la petición (HttpContext.User).
  • Middleware de Autorización (UseAuthorization): Evalúa las políticas de acceso y comprueba si la identidad autenticada posee los privilegios requeridos para ejecutar el recurso.
  • Middleware de Minimal APIs: Finalmente, dirige la llamada al endpoint correspondiente si las capas anteriores autorizaron el paso.

Middleware: ManejadorGlobalExcepcionesMiddleware.cs

Intercepta el pipeline de peticiones de ASP.NET Core capturando excepciones del sistema y devolviendo respuestas uniformes en formato JSON. 

public sealed class ManejadorGlobalExcepcionesMiddleware
{
    private readonly RequestDelegate _siguiente;
    private readonly ILogger<ManejadorGlobalExcepcionesMiddleware> _logger;

    public ManejadorGlobalExcepcionesMiddleware(RequestDelegate siguiente, ILogger<ManejadorGlobalExcepcionesMiddleware> logger)
    {
        _siguiente = siguiente;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext contexto)
    {
        try
        {
            await _siguiente(contexto);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Ocurrió una excepción no controlada al procesar la solicitud.");

            var (codigoEstado, titulo) = MapearExcepcion(ex);

            contexto.Response.StatusCode = codigoEstado;
            contexto.Response.ContentType = "application/json";

            var respuesta = new ProblemDetails
            {
                Status = codigoEstado,
                Title = titulo,
                Detail = ex.Message,
                Instance = contexto.Request.Path
            };

            await contexto.Response.WriteAsJsonAsync(respuesta);
        }
    }

    private static (int CodigoEstado, string Titulo) MapearExcepcion(Exception ex)
    {
        return ex switch
        {
            AutorizacionException => ((int)HttpStatusCode.Forbidden, "Error de autorización"),
            UnauthorizedAccessException => ((int)HttpStatusCode.Unauthorized, "No autorizado"),
            AplicationException when ex.Message.Contains("no existe", StringComparison.OrdinalIgnoreCase) || 
                                     ex.Message.Contains("no encontrado", StringComparison.OrdinalIgnoreCase)
                => ((int)HttpStatusCode.NotFound, "Recurso no encontrado"),
            AplicationException => ((int)HttpStatusCode.BadRequest, "Error de aplicación"),
            DomainException => ((int)HttpStatusCode.BadRequest, "Error de dominio"),
            RepositoryException => ((int)HttpStatusCode.NotFound, "Recurso no encontrado"),
            EntidadNoEncontradaException => ((int)HttpStatusCode.NotFound, "Entidad no encontrada"),
            _ => ((int)HttpStatusCode.InternalServerError, "Error inesperado")
        };
    }
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Capturar los errores en un Middleware global (`ManejadorGlobalExcepcionesMiddleware`) que mapea las excepciones a códigos de estado HTTP semánticos y devuelve respuestas estandarizadas usando la clase `ProblemDetails` (RFC 7807).
  • Alternativa Descartada: Escribir bloques `try-catch` individuales en cada endpoint/controlador de la Web API o delegar el manejo de excepciones a las herramientas por defecto de ASP.NET Core que retornan páginas HTML de error en modo de desarrollo.
  • ¿Por qué SÍ? (Ventajas de la decisión): Centraliza el control de errores en un solo componente del pipeline HTTP, asegurando que ninguna excepción en bruto (que revele trazas de código o rutas internas del servidor) se filtre al cliente. La respuesta estructurada con `ProblemDetails` provee un formato consistente que cualquier cliente frontend puede procesar de manera uniforme.
  • ¿Por qué NO? (Desventajas/Limitaciones): Requiere mantener actualizado un mapa estático de excepciones a códigos HTTP (`MapearExcepcion`). Si se crea una nueva excepción de negocio y se olvida registrarla en el switch-case, el middleware la tratará por defecto como un error de servidor `500 Internal Server Error`, ocultando el verdadero motivo del fallo.
  • Cómo Defenderlo en el Examen Oral: "Implementamos un Middleware global para manejar excepciones al inicio del pipeline HTTP. De esta forma, capturamos cualquier error lanzado en las capas de aplicación o de dominio de manera centralizada. Evitamos contaminar los endpoints con bloques try-catch repetitivos, mapeamos las excepciones semánticamente a códigos HTTP como 400 BadRequest o 404 NotFound, y devolvemos respuestas estandarizadas bajo el estándar internacional RFC 7807 (Problem Details), lo cual es una buena práctica de diseño REST."
Swagger Filter: FiltroAutorizacion.cs

Añade de forma dinámica los esquemas y candados de seguridad Bearer JWT en Swagger UI para endpoints autenticados. 

public sealed class FiltroAutorizacion : IDocumentFilter
{
    public void Apply(OpenApiDocument documento, DocumentFilterContext contexto)
    {
        foreach (var apiDescription in contexto.ApiDescriptions)
        {
            var metadatosDelEndpoint = apiDescription.ActionDescriptor.EndpointMetadata;
            var tieneAutorizacion = metadatosDelEndpoint.OfType<AuthorizeAttribute>().Any();
            var permiteAnonimo = metadatosDelEndpoint.OfType<AllowAnonymousAttribute>().Any();

            if (!tieneAutorizacion || permiteAnonimo) continue;

            if (string.IsNullOrWhiteSpace(apiDescription.RelativePath) || string.IsNullOrWhiteSpace(apiDescription.HttpMethod))
            {
                continue;
            }

            var ruta = "/" + apiDescription.RelativePath.Split('?')[0].TrimEnd('/');
            if (ruta == "//") ruta = "/";

            if (!documento.Paths.TryGetValue(ruta, out var pathItem)) continue;

            if (!pathItem.Operations.TryGetValue(new System.Net.Http.HttpMethod(apiDescription.HttpMethod), out var operation))
            {
                continue;
            }

            operation.Security ??= [];

            var yaMarcado = operation.Security.Any(requisito =>
                requisito.Keys.OfType<OpenApiSecuritySchemeReference>().Any(referencia =>
                    string.Equals(referencia.Reference?.Id, "Bearer", StringComparison.Ordinal)));

            if (yaMarcado) continue;

            operation.Security.Add(new OpenApiSecurityRequirement
            {
                [new OpenApiSecuritySchemeReference("Bearer", documento)] = new List<string>()
            });
        }
    }
}
Debate de Diseño y Defensa (Preparación de Examen)
  • Decisión de Diseño Tomada: Configurar un filtro de OpenAPI (`FiltroAutorizacion`) que implementa `IDocumentFilter` para inyectar de forma dinámica los requisitos y candados de seguridad Bearer JWT (`OpenApiSecurityRequirement`) en la interfaz visual de Swagger UI para todos aquellos endpoints que requieran autorización y no sean públicos (`[Authorize]`).
  • Alternativa Descartada: Marcar manualmente cada endpoint con esquemas de Swagger en el código C# mediante atributos redundantes, o no configurar candados en Swagger UI, obligando al usuario a agregar cabeceras manuales para autenticarse al probar la API.
  • ¿Por qué SÍ? (Ventajas de la decisión): Automatiza y mantiene la documentación OpenAPI sincronizada con el estado real de la seguridad del backend. Al leer metadatos de endpoints directamente, se evita el riesgo de documentar como público un recurso privado o viceversa, y simplifica la experiencia de pruebas interactivas en el navegador.
  • ¿Por qué NO? (Desventajas/Limitaciones): Acopla la generación del Swagger a una clase personalizada de filtrado que utiliza clases y tipos de la librería `Microsoft.OpenApi` y del descriptor de acciones de ASP.NET Core, lo cual puede romperse o requerir modificaciones ante actualizaciones mayores de versiones de .NET.
  • Cómo Defenderlo en el Examen Oral: "Implementamos la interfaz IDocumentFilter de OpenAPI para automatizar la colocación de candados de seguridad en Swagger UI. El filtro recorre dinámicamente los metadatos de los endpoints mapeados al arrancar la API. Si el endpoint requiere autenticación y no permite accesos anónimos, inyectamos el requisito de seguridad Bearer. De este modo, la documentación Swagger se auto-adapta a las políticas de seguridad sin necesidad de marcar manualmente cada endpoint con atributos extras repetitivos."

public static class ExpedientesEndpoints

        return routes;
    }

    private static Guid ObtenerIdUsuarioDelToken(ClaimsPrincipal user)
    {
        var claim = user.FindFirst(ClaimTypes.NameIdentifier);
        if (claim == null)
        {
            throw new UnauthorizedAccessException("No se pudo obtener el ID del usuario del token.");
        }
        return Guid.Parse(claim.Value);

6. Guía de Estudio y Defensa del Proyecto (Preguntas Frecuentes)

Esta sección funciona como una guía rápida para el examen o defensa oral del proyecto. Contiene las preguntas teóricas y técnicas más frecuentes de los evaluadores, junto con sus fundamentos arquitectónicos explicados conceptualmente:

P1: ¿Por qué eligieron una Arquitectura Limpia/Hexagonal y no una tradicional de 3 Capas?

Respuesta: En una arquitectura tradicional de 3 capas (Presentación -> Negocio -> Acceso a Datos), la lógica de negocio depende directamente de los detalles de infraestructura. Si cambia la base de datos o el ORM, se debe modificar y recompilar todo el sistema.

Al utilizar Arquitectura Limpia, aplicamos el principio de Inversión de Dependencias (D de SOLID). El Dominio (las reglas puras del negocio) y la Aplicación (los casos de uso) están en el centro del sistema y no conocen los detalles técnicos externos. Definen interfaces abstractas (puertos como IExpedienteRepository). La capa de Infraestructura implementa estos puertos (adaptadores). Esto provee:

  • Desacoplamiento total: Se puede cambiar SQLite por PostgreSQL o SQL Server modificando únicamente los adaptadores de infraestructura, sin alterar el código comercial.
  • Testabilidad independiente: Permite probar unitariamente la lógica comercial inyectando repositorios simulados (mocks) en memoria, sin necesidad de conectarse a una base de datos física real.
P2: ¿Cuál es la diferencia conceptual entre una Entidad, un Value Object y un DTO?

Respuesta: Cada uno posee una responsabilidad única en la arquitectura:

  • Entidad (ej. Expediente, Usuario): Posee una identidad única mutable (`Guid Id`) y un ciclo de vida con estados. Dos entidades son idénticas si comparten el mismo identificador único, aunque sus propiedades internas difieran en el tiempo.
  • Value Object (ej. Caratula, Contenido): Carece de identidad. Se define puramente por el valor de sus propiedades y es inmutable. Si cambia, se crea una nueva instancia completa. La comparación se hace por igualdad estructural de sus campos y no por puntero. Se utiliza para auto-validar lógica comercial primitiva.
  • DTO (Data Transfer Object): Estructura plana de datos (sin comportamiento) diseñada únicamente para transferir información a través de los límites del sistema (desde el cliente HTTP hacia la API y viceversa). Evita exponer las entidades internas del dominio directo a los clientes externos.
P3: ¿Cómo funciona el Patrón Unidad de Trabajo (Unit of Work) y cuál es su beneficio?

Respuesta: El patrón IUnidadDeTrabajo coordina múltiples llamadas a repositorios bajo una única transacción de base de datos lógica.

Si no usáramos Unidad de Trabajo y cada repositorio realizara su propio guardado de cambios a base de datos, un error en la mitad de un caso de uso (como registrar un trámite con éxito pero fallar al actualizar el estado del expediente asociado) dejaría la base de datos en un estado corrupto e inconsistente. Al agruparlas bajo la Unidad de Trabajo, los cambios quedan guardados en el Change Tracker de EF Core y se aplican de manera atómica (todo o nada) en una transacción transaccional.

P4: ¿Por qué implementaron una Autorización basada en Permisos en lugar de Roles?

Respuesta: La autorización basada en Roles (ej: [Authorize(Roles = "Admin")]) es rígida. Si mañana el negocio requiere un nuevo rol (ej. "OperadorJunior") con un subconjunto de acciones de otro rol, se requeriría modificar el código C# en todos los controladores donde se definieron los accesos.

Con la autorización basada en Permisos granulares (ej: ExpedienteAlta, TramiteAlta), protegemos cada endpoint individualmente con el permiso correspondiente. Los usuarios tienen asignada una lista de permisos específicos. La creación de nuevos roles o el ajuste de privilegios de un usuario se realiza dinámicamente desde la persistencia o asignándolos en el token JWT, sin requerir cambios ni recompilaciones en el código de la API.

P5: ¿Cómo mantienen la pureza del Dominio si utilizan Entity Framework Core como ORM?

Respuesta: Para evitar acoplar la capa comercial con infraestructura, las entidades de dominio no utilizan atributos decorativos del ORM (como [Key], [Table] o [Required]).

Toda la configuración del mapeo de tablas, llaves foráneas y tipos relacionales se realiza en la capa de Infraestructura (dentro de SGEContext.cs) utilizando la API Fluida (Fluent API). Asimismo, los Value Objects complejos (como Caratula y Contenido) se mapean mediante propiedades complejas (Complex Types) usando ComplexProperty() (característica moderna de EF Core 8+). Esto aplana sus campos directamente en la tabla principal como columnas normales, sin requerir una tabla adicional ni IDs propios en el objeto de valor, logrando que el dominio se mantenga como código C# puro (POCO) e inmutable, ajeno a los mecanismos relacionales físicos.

P6: ¿Cómo interactúan el Middleware de Seguridad y el Filtro de Autorización?

Respuesta: El proceso consta de dos fases secuenciales:

  1. Autenticación (Middleware): Cuando llega la petición HTTP, el middleware de ASP.NET Core intercepta la cabecera Authorization, valida la firma criptográfica del JWT y mapea los claims de seguridad (como los permisos del usuario) en el principal del contexto (HttpContext.User).
  2. Autorización (Filtro): El filtro FiltroAutorizacion intercepta la llamada justo antes de llegar al controlador, recupera el permiso requerido por la acción del controlador y verifica si el usuario autenticado tiene ese permiso en sus claims. Si no lo tiene, interrumpe el flujo y devuelve un error 403 Forbidden sin llegar a procesar el controlador.
P7: ¿Cómo se configuran los Endpoints en la Web API y cómo se mapean los parámetros (Model Binding) usando Minimal APIs?

Respuesta: En lugar de controladores tradicionales, los endpoints se configuran mediante Minimal APIs en clases estáticas (como ExpedientesEndpoints). La configuración y el mapeo de datos se realiza de la siguiente manera:

  • routes.MapGroup("/api/recurso"): Agrupa las rutas asociadas a un recurso bajo un prefijo común y permite aplicar configuraciones transversales como RequireAuthorization() de forma unificada.
  • Verbos de Ruteo (group.MapGet, group.MapPost, etc.): Asocian métodos HTTP a expresiones lambda o delegados que ejecutan la lógica correspondiente.
  • Mapeo de Parámetros (Model Binding):
    • Inferencia Automática: El framework analiza los parámetros de la firma. Si el parámetro es un DTO complejo, se asume que proviene del cuerpo JSON. Si es un tipo primitivo que coincide con un segmento de la ruta, se enlaza desde allí.
    • [AsParameters]: Le indica al enlazador de ASP.NET Core que debe reconstruir un objeto complejo (como un DTO de búsqueda) a partir de los datos individuales de la consulta (Query String) o de la ruta, facilitando firmas limpias.
    • Inyección de Servicios: Cualquier parámetro registrado en el contenedor IoC (como los use cases) se inyecta automáticamente en la firma del delegado.
    • Seguridad de Contexto: El ClaimsPrincipal se recibe como parámetro inyectado directamente y la identidad del usuario se extrae en el servidor leyendo el claim del token JWT (FindFirst(ClaimTypes.NameIdentifier)).
P8: ¿Cómo defender la ubicación de un archivo si sale al azar en una "bolilla" de examen?

Respuesta: Si el tribunal elige un archivo al azar de la solución, la clave para defenderlo es clasificarlo en su capa correspondiente y explicar su responsabilidad en la arquitectura:

  • Capa de Dominio (SGE.Dominio) — El Corazón del Negocio:
    • Archivos ejemplo: Expediente.cs, Caratula.cs, EstadoExpediente.cs, DomainException.cs.
    • Defensa: "Este archivo está en el Dominio porque representa las reglas esenciales e invariantes del negocio. Es código C# puro (POCO), no tiene dependencias de bases de datos, APIs ni librerías externas. Si las normas del sistema de gestión de expedientes cambian en la vida real, se modifica en esta capa".
  • Capa de Aplicación (SGE.Aplicacion) — Los Orquestadores de Casos de Uso:
    • Archivos ejemplo: AgregarExpedienteUseCase.cs, IExpedienteRepository.cs, AgregarExpedienteRequest.cs.
    • Defensa: "Pertenece a la capa de Aplicación porque coordina el flujo de los datos del sistema. Los archivos UseCase implementan las intenciones del usuario llamando al dominio y persistiendo a través de interfaces. Aquí definimos las interfaces (puertos) porque la Aplicación dicta qué necesita para operar, pero delega el cómo se hace a la infraestructura".
  • Capa de Infraestructura (SGE.Infraestructura) — Los Detalles Tecnológicos:
    • Archivos ejemplo: SGEContext.cs, ExpedienteRepository.cs, ProveedorTokenJwt.cs, SGESqlite.cs.
    • Defensa: "Este archivo es de Infraestructura porque contiene la implementación tecnológica concreta (los adaptadores). Aquí nos acoplamos a paquetes externos (como Entity Framework Core para SQLite o JwtBearer para seguridad). Es la capa encargada de interactuar con el disco duro, la base de datos física o los algoritmos de encriptación".
  • Capa de Presentación (SGE.WebApi) — El Punto de Entrada Técnico:
    • Archivos ejemplo: ExpedientesEndpoints.cs (Minimal APIs), Program.cs, ManejadorGlobalExcepcionesMiddleware.cs, FiltroAutorizacion.cs.
    • Defensa: "Está en la capa de Presentación porque actúa como el punto de inicio de la aplicación para el cliente externo. Configura el pipeline HTTP de ASP.NET Core, realiza la inyección de dependencias, valida el token JWT de entrada y mapea las peticiones REST utilizando Minimal APIs hacia los Casos de Uso correspondientes".

4.5 Errores, validaciones y comportamiento técnico

  • El middleware global devuelve 401 cuando falta autenticación y 403 cuando el usuario autenticado no tiene el permiso necesario.
  • Los errores de dominio y validación se traducen normalmente en 400 Bad Request.
  • Los recursos ausentes se exponen como 404 Not Found en los casos donde la capa de aplicación o repositorio lanza una excepción de no existencia.
  • Swagger configura la opción de persistir autorización, por lo que el token puede reutilizarse durante la sesión de documentación.
  • La base de datos SQLite se crea automáticamente al iniciar la API, así que no hace falta una migración manual para comenzar a probar el sistema.

4.6 Partes Fundamentales del Proyecto y por qué son clave

Esta sección resume las piezas que más conviene conocer de memoria porque atraviesan todo el sistema. Si te preguntan “qué es lo importante del proyecto”, acá están las respuestas más directas.

Idea general

El proyecto funciona bien porque cada parte tiene una responsabilidad concreta: la Web API recibe, la capa de Aplicación coordina, el Dominio protege las reglas y la Infraestructura guarda y conecta con la tecnología real.

Lectura paso a paso de las partes clave
  • Unidad de Trabajo (UnidadDeTrabajo): reúne los cambios de varios repositorios y los confirma con una sola llamada a SaveChanges(). Es clave porque evita guardar cosas por separado y mantiene la transacción coherente.
  • SGEContext: es el mapa central de la base de datos. Define las tablas, las conversiones de objetos de valor y los datos semilla, así que es una de las piezas más importantes de la persistencia.
  • SGESqlite: asegura que la base exista antes de empezar a atender pedidos. Su valor está en el arranque seguro y en evitar inicializaciones repetidas.
  • Program.cs: arma toda la aplicación: registra servicios, configura JWT, levanta Swagger, inicializa la base y ordena el pipeline HTTP. Es el punto de arranque real del sistema.
  • ManejadorGlobalExcepcionesMiddleware: convierte errores técnicos en respuestas uniformes. Es clave porque hace que toda la API responda de forma consistente.
  • FiltroAutorizacion: marca visualmente en Swagger qué endpoints necesitan Bearer token. Ayuda mucho a estudiar, probar y defender la API sin confundirse con permisos.
  • Endpoints (Minimal APIs): reciben la petición HTTP de forma directa, extraen la identidad desde el claims principal del token, inyectan y ejecutan el caso de uso correspondiente y devuelven respuestas uniformes. Son la frontera de entrada del sistema.
  • Casos de uso y expedientes/trámites: son los que realmente coordinan la lógica del negocio. Si querés explicar cómo funciona el sistema, empezá por ahí.
  • Dominio: contiene las reglas duras del negocio. Sin esta capa, el sistema perdería consistencia y validación.
Cómo defender estas partes en una oral

Una forma simple de responder es: decir qué problema resuelve la pieza, en qué capa vive y qué pasaría si no existiera. Por ejemplo, si sacás la Unidad de Trabajo, podés terminar guardando sólo una parte de la operación; si sacás el SGEContext, ya no hay forma de mapear el dominio a SQLite; si sacás los endpoints, la aplicación deja de tener entrada HTTP.

Lectura rápida de cada pieza clave
  • Unidad de Trabajo: confirma cambios.
  • SGEContext: traduce dominio a base.
  • SGESqlite: inicializa la base de forma segura.
  • Interfaces: separan lo que se quiere hacer de cómo se hace.
  • Endpoints (Minimal APIs): reciben HTTP y delegan.
  • Web API: expone el sistema al exterior.

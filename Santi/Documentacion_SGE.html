1. Flujo General de Ejecución del Sistema

El sistema funciona bajo el principio de arquitectura por capas desacoplada. Una petición viaja de la siguiente manera:

Diagramas de Secuencia y Flujos de Datos

Para facilitar el seguimiento del flujo de la información, a continuación se detallan los diagramas de secuencia interactivos de las operaciones críticas del sistema, ilustrando cómo se comunican las distintas capas (Presentación, Aplicación, Dominio e Infraestructura) a medida que viajan los datos.

Flujo 1: Registro de un Nuevo Usuario

Muestra el camino de los datos cuando un administrador crea un nuevo usuario en el sistema. Los datos pasan del controlador al caso de uso, se hashea la contraseña de forma unidireccional y se persiste en SQLite.

Flujo 2: Inicio de Sesión (Login)

Muestra el flujo de credenciales para obtener un token JWT firmado. La API valida contra SQLite la existencia del usuario, verifica el hash de la contraseña y genera el JWT.

Flujo 3: Creación de un Expediente

Muestra el flujo al dar de alta un expediente. Requiere cabecera JWT válida. El caso de uso evalúa permisos, crea la raíz de agregado y lo guarda de forma segura.

Flujo 4: Consulta de un Expediente y sus Trámites

Muestra el flujo de lectura de datos. EF Core lee la base de datos relacional, convierte los Value Objects primitivos a objetos ricos y retorna un DTO seguro estructurado.

Flujo 5: Anexar un Trámite a un Expediente

Muestra el flujo completo cuando se agrega un trámite. Involucra la máquina de estados del Expediente (para cambiar a Finalizado si es PaseAlArchivo) y la persistencia atómica coordinada por la Unidad de Trabajo.

2. Detalle de Clases: Capa de Dominio (SGE.Dominio)

Representa el núcleo puro del negocio. Contiene las entidades principales, que encapsulan estado y reglas de negocio, y los Value Objects (Objetos de Valor).

Fundamentos Teóricos del Diseño Guiado por el Dominio (DDD)

La capa de Dominio es el corazón de la aplicación. Representa los conceptos, las reglas del negocio y los casos de lógica pura que definen el comportamiento de nuestro sistema. De acuerdo con los principios del Domain-Driven Design (DDD), esta capa no tiene dependencias de ningún elemento externo (como bases de datos, APIs o frameworks), lo que garantiza su portabilidad y estabilidad ante cambios técnicos. Sus componentes clave se dividen en:

1. Entidades y Raíces de Agregación (Aggregate Roots): Una Entidad es un objeto que posee una identidad única que trasciende el tiempo y los cambios de estado (representada por un ID único de tipo Guid). El Agregado es un conjunto de entidades y objetos de valor que se tratan como una única transacción lógica. La raíz del agregado (Aggregate Root), como la clase Expediente, es el único punto de contacto con el exterior del agregado. Cualquier cambio en sus partes internas (como añadir un Tramite o modificar una fecha de actualización) debe realizarse obligatoriamente a través de métodos expuestos en la raíz. Esto previene que los objetos queden en estados corruptos o inconsistentes.

2. Objetos de Valor (Value Objects): A diferencia de las entidades, los Value Objects carecen de una identidad conceptual propia. Se definen únicamente por sus propiedades (como Caratula o Contenido) y son inmutables: si un objeto de valor cambia, se reemplaza por uno completamente nuevo en lugar de mutar sus propiedades en memoria. La comparación entre dos objetos de valor se hace por igualdad estructural (sus valores internos son idénticos) y no por referencia de puntero, lo que simplifica enormemente la lógica de control.

3. Preservación de Invariantes y Excepciones: Una invariante es una regla de negocio que debe cumplirse en todo momento (por ejemplo, "un expediente finalizado no puede volver a cambiar de estado"). En DDD, las entidades y objetos de valor son responsables de auto-validarse. El constructor y los métodos de negocio evalúan las invariantes preventivamente y lanzan excepciones especializadas (DomainException) si se detecta una anomalía. De este modo, se garantiza que el dominio actúe como un escudo protector, imposibilitando que datos corruptos viajen hacia las bases de datos.

Clase: Expediente.cs

Esta entidad representa un expediente administrativo en el sistema. Es la raíz de agregación y gestiona la coherencia y estados lógicos del expediente. 

namespace SGE.Dominio.Expedientes;

public class Expediente
{
    public Guid Id { get; private set; }
    public DateTime FechaCreacion { get; private set; }
    public DateTime FechaUltimaModificacion { get; private set; }
    public Guid UsuarioUltimoCambio { get; private set; }
    public Caratula Caratula { get; private set; }
    public EstadoExpediente Estado { get; private set; }

    private Expediente()
    {
        Caratula = null!;
    }

    public Expediente(Caratula caratula, Guid user)
        : this(Guid.NewGuid(), DateTime.Now, DateTime.Now, user, caratula, EstadoExpediente.RecienIniciado)
    {
    }

    private Expediente(Guid id, DateTime fechaCreacion, DateTime fechaUltimaModificacion, Guid usuarioUltimoCambio, Caratula caratula, EstadoExpediente estado)
    {
        if (id == Guid.Empty)
        {
            throw new DomainException("El Id no puede ser vacío.");
        }

        if (fechaUltimaModificacion.CompareTo(fechaCreacion) < 0)
        {
            throw new DomainException("La fecha de modificación no puede ser previa a la de creación.");
        }

        Id = id;
        FechaCreacion = fechaCreacion;
        FechaUltimaModificacion = fechaUltimaModificacion;
        UsuarioUltimoCambio = usuarioUltimoCambio;
        Caratula = caratula;
        Estado = estado;
    }

    public static Expediente Reconstruir(Guid id, DateTime fechaCreacion, DateTime fechaUltimaModificacion, Guid usuarioUltimoCambio, Caratula caratula, EstadoExpediente estado)
    {
        return new Expediente(id, fechaCreacion, fechaUltimaModificacion, usuarioUltimoCambio, caratula, estado);
    }

    private void RegistrarModificacion(Guid idUser)
    {
        UsuarioUltimoCambio = idUser;
        FechaUltimaModificacion = DateTime.Now;
    }

    public void ModificarCaratula(Caratula nuevaC, Guid idUser)
    {
        Caratula = nuevaC;
        RegistrarModificacion(idUser);
    }

    public bool ActualizarEstado(EtiquetaTramite? ultEtiqueta, Guid idUser)
    {
        EstadoExpediente estadoAntes = Estado;
        switch (ultEtiqueta)
        {
            case null:
                Estado = EstadoExpediente.RecienIniciado;
                break;
            case EtiquetaTramite.Resolucion:
                Estado = EstadoExpediente.ConResolucion;
                break;
            case EtiquetaTramite.PaseAEstudio:
                Estado = EstadoExpediente.ParaResolver;
                break;
            case EtiquetaTramite.PaseAlArchivo:
                Estado = EstadoExpediente.Finalizado;
                break;
        }

        RegistrarModificacion(idUser);
        return estadoAntes != Estado;
    }

    public bool ActualizarEstado(EstadoExpediente nuevoEstado, Guid idUser)
    {
        EstadoExpediente estadoAntes = Estado;
        Estado = nuevoEstado;
        RegistrarModificacion(idUser);
        return estadoAntes != Estado;
    }
}
Explicación detallada del bloque (Patrones de Diseño y DDD):
  • El Expediente como Aggregate Root (Raíz de Agregado): En el diseño dirigido por el dominio (DDD), un Agregado es un grupo de objetos asociados que se tratan como una unidad transaccional de datos. El Expediente actúa como la Raíz del Agregado (Aggregate Root). Esto significa que es la única puerta de entrada para modificar cualquier dato del expediente o de sus elementos subordinados (como los trámites asociados). Al encapsular las modificaciones a través del expediente, se asegura que las invariantes de negocio (las reglas de consistencia interna) se validen y cumplan en todo momento.
  • Encapsulamiento de Propiedades y Modificadores private set: Al declarar los setters de las propiedades (como Estado y Caratula) con el modificador private set, prohibimos explícitamente que las capas externas (como la Web API o los servicios de infraestructura) modifiquen directamente el estado del expediente en memoria. Si un programador desea cambiar el estado del expediente, se ve obligado a invocar el método de negocio ActualizarEstado(), lo que garantiza que la transición sea validada por las reglas comerciales vigentes.
  • Materialización de Entidades y el Constructor Privado sin Parámetros: Entity Framework Core (EF Core) necesita instanciar (hidratar) las entidades al recuperarlas desde la base de datos SQLite. Para ello, requiere un constructor sin parámetros. Al definir private Expediente() con el operador de perdón de nulos null! para la Caratula, permitimos que EF Core cree el objeto de forma técnica y transparente en segundo plano. Dado que es un constructor privado, ningún programador externo puede utilizarlo, protegiendo al objeto de ser instanciado de forma incorrecta o sin datos en otras capas.
  • Factoría Técnica (Factory Method) Reconstruir: Durante la creación inicial de un expediente, el constructor público asigna un nuevo identificador (Guid.NewGuid()), marca las fechas actuales (DateTime.Now) y define el estado inicial como RecienIniciado. Sin embargo, al recuperar un expediente existente de la base de datos, no queremos asignarle valores nuevos ni mutar su historial de auditoría. El método estático Reconstruir actúa como una factoría técnica dedicada a inicializar un expediente con sus datos históricos reales provenientes de la base de datos sin disparar las reglas y firmas automáticas que se ejecutan durante una creación desde cero.
  • Encapsulación de la Máquina de Estados Lógicos: El estado de un expediente administrativo no es una variable arbitraria que pueda cambiarse libremente. El método sobrecargado ActualizarEstado(EtiquetaTramite? ultEtiqueta, Guid idUser) implementa una máquina de estados determinista. Evalúa la etiqueta del último trámite ingresado y realiza la transición adecuada: por ejemplo, ante un trámite de tipo PaseAlArchivo, el estado se actualiza irreversiblemente a Finalizado. Al final de la transición, registra los datos de auditoría (UsuarioUltimoCambio y FechaUltimaModificacion) e informa mediante un valor booleano si la transición de estado fue efectiva.
Clase: Caratula.cs

Es un Objeto de Valor (Value Object) que representa la carátula o el título identificador de un expediente. 

namespace SGE.Dominio.Expedientes;

public record class Caratula
{
    public string Valor { get; }
    
    public Caratula(string valor)
    {
        if (string.IsNullOrWhiteSpace(valor))
        {
            throw new DomainException("El nombre de la caratula no puede estar vacío.");
        }
        Valor = valor.Trim();
    }

    public override string ToString() => Valor;
}
Explicación detallada del bloque (Value Objects y Records):
  • El concepto de Objeto de Valor (Value Object): En DDD, no todos los objetos del sistema requieren una identidad única e histórica (como un ID autoincremental). Un Value Object es un objeto que se define únicamente por el conjunto de sus atributos. La Caratula no posee un ciclo de vida independiente ni un identificador único; dos carátulas son idénticas si su texto es el mismo. Al modelarla como un Value Object, simplificamos el modelo mental y evitamos la sobrecarga de generar tablas relacionales adicionales.
  • El tipo record class en C#: C# provee el tipo record para modelar de forma nativa estructuras de datos inmutables con comparaciones de igualdad basadas en valores en vez de referencias en memoria. Esto significa que si creamos dos objetos de tipo Caratula con el valor `"Expediente de Personal"`, la comparación caratula1 == caratula2 evaluará a true de manera automática, sin necesidad de sobrecargar operadores de igualdad complejos.
  • Validación Preventiva en el Constructor: Un Objeto de Valor no puede entrar en un estado inconsistente. El constructor de Caratula valida preventivamente que el texto provisto no sea nulo ni contenga espacios en blanco mediante string.IsNullOrWhiteSpace(). Si la validación falla, interrumpe el flujo arrojando una DomainException inmediatamente. De este modo, garantizamos que si logramos instanciar una carátula, esta es 100% válida para el sistema. Adicionalmente, aplica un Trim() para normalizar y limpiar el texto de espacios accidentales en los extremos.

  • Entidad Subordinada en el Agregado: A diferencia de los objetos de valor inmutables, la clase Tramite representa una Entidad puesto que posee una identidad conceptual única representada por su propiedad Id. Sin embargo, no funciona de manera independiente; pertenece al agregado de Expediente y está enlazado a él a través de la clave foránea ExpedienteId.
  • Encapsulamiento del Ciclo de Vida: De forma homóloga a Expediente, la clase Tramite define sus setters como privados. La única forma de alterar su contenido es invocando el método explícito de negocio ModificarContenido(Contenido nuevoContenido, Guid usuarioId), que no solo realiza el cambio de texto sino que de forma atómica y obligatoria actualiza la fecha de modificación y la firma de auditoría del usuario que realizó la acción, evitando inconsistencias u omisiones en el log de auditoría.
  • Constructor Privado y Reconstrucción: Cuenta con el constructor privado sin parámetros requerido por Entity Framework Core para materializar el trámite desde la base de datos sin ejecutar validaciones de creación, y provee el método estático Reconstruir para restaurar el estado original del trámite guardado en SQLite sin mutar la fecha de creación real.

3. Detalle de Clases: Capa de Aplicación (SGE.Aplicacion)

Esta capa implementa las reglas de orquestación del sistema mediante Casos de Uso, DTOs y validaciones de seguridad específicas.

Fundamentos Teóricos de la Capa de Aplicación

La capa de Aplicación funciona como la orquestadora principal del sistema. Su misión es traducir las intenciones del usuario (recibidas en la API) en acciones de negocio sobre el dominio, coordinando el flujo de datos y controlando la infraestructura técnica mediante interfaces. Sus principios fundamentales son:

1. Casos de Uso (Orquestadores de Flujo): Cada caso de uso (como AgregarExpedienteUseCase o LoginUseCase) representa una operation lógica e individual del negocio. Los casos de uso no contienen las reglas esenciales del negocio (las cuales residen en el dominio), sino que se limitan a cargar entidades desde los repositorios, invocar los métodos comerciales del dominio y llamar al guardado de cambios. De esta forma, el caso de uso es un director de orquesta: dice qué hacer y en qué orden, pero la lógica fina la ejecutan los agregados de dominio.

2. Inversión de Dependencias a través de Puertos (Interfaces): La capa de aplicación no conoce bases de datos, redes o archivos físicos. Define interfaces de acceso (como IExpedienteRepository o IUnidadDeTrabajo) que actúan como "puertos". La capa de Infraestructura implementa estas interfaces (los "adaptadores"). Esto nos permite cambiar el motor de persistencia (por ejemplo, pasar de SQLite a SQL Server o una base de datos Mock para pruebas) sin modificar una sola línea de código en la capa de aplicación o de dominio.

3. Objetos de Transferencia de Datos (DTOs): Representan estructuras de datos planas (records o clases sin lógica) que viajan a través de los límites del sistema. Evitan el acoplamiento directo entre los clientes externos y las entidades de dominio (como Expediente), impidiendo problemas de seguridad (over-posting) y protegiendo el encapsulamiento interno al no exponer propiedades con set privado o relaciones circulares que complicarían la serialización.

public class EliminarExpedienteUseCase
{
    private readonly IUnidadDeTrabajo _uow;
    private readonly IExpedienteRepository _iExpRepo;
    private readonly ITramiteRepository _iTramRepo;
    private readonly IAutorizacionService _autorizacion;

    public EliminarExpedienteUseCase(IUnidadDeTrabajo uow, IExpedienteRepository iExpRepo, ITramiteRepository iTramRepo, IAutorizacionService autorizacion)
    {
        _uow = uow;
        _iExpRepo = iExpRepo;
        _iTramRepo = iTramRepo;
        _autorizacion = autorizacion;
    }

    public EliminarExpedienteResponse Ejecutar(EliminarExpedienteRequest req, Guid idUsuario)
    {
        if (req == null)
        {
            throw new AplicationException("La solicitud no puede estar vacía."); 
        }

        if (!_autorizacion.PoseeElPermiso(idUsuario, Permiso.ExpedienteBaja))
        {
            throw new AutorizacionException("El usuario no tiene permisos para eliminar este expediente.");
        }

        var expedienteABorrar = _iExpRepo.ObtenerPorId(req.ExpedienteId);
        if (expedienteABorrar == null)
        {
            throw new AplicationException("No se encontró el expediente solicitado");
        }

        // Eliminación en Cascada programática a nivel de Aplicación
        var tramites = _iTramRepo.ObtenerPorExpedienteId(req.ExpedienteId).ToList();
        foreach (var t in tramites)
        {
            _iTramRepo.Eliminar(t.Id);
        }

        _iExpRepo.Eliminar(req.ExpedienteId);
        _uow.Guardar();

        return new EliminarExpedienteResponse(req.ExpedienteId);
    }
}
Explicación detallada del bloque (Cascada Programática y Consistencia):
  • Validación Defensiva del DTO de Entrada: Comprueba inmediatamente si la solicitud entrante req es nula. En arquitecturas REST, un cuerpo JSON mal estructurado puede ser deserializado como nulo; atrapar este caso temprano evita excepciones genéricas del sistema como `NullReferenceException`, arrojando en su lugar una excepción controlada de aplicación (AplicationException).
  • Manejo de Eliminación en Cascada en Capa de Aplicación: La eliminación de un registro padre (el expediente) requiere la eliminación de todos sus hijos (los trámites) para mantener la integridad referencial. Aunque esto podría delegarse a reglas de cascada automáticas (ON DELETE CASCADE) de SQLite, realizarlo de forma explícita y programática a nivel de aplicación ofrece mayor visibilidad, portabilidad entre diferentes motores de bases de datos y facilita el logging de auditoría de cada trámite removido.
  • Transaccionalidad Asegurada: Al recuperar y eliminar todos los trámites vinculados mediante _iTramRepo.Eliminar(t.Id) en un bucle antes de eliminar el expediente con _iExpRepo.Eliminar(), se encolan todas las instrucciones de borrado en el Change Tracker. El llamado final a _uow.Guardar() ejecuta todas estas operaciones en un único bloque transaccional. Si alguna falla, se revierte todo, impidiendo que queden trámites huérfanos.

public class CambiarPermisosUseCase
{
    private readonly IUnidadDeTrabajo _uow;
    private readonly IUsuarioRepository _userRepo;
    private readonly IAutorizacionService _autorizacion;

    public CambiarPermisosUseCase(IUnidadDeTrabajo uow, IUsuarioRepository userRepo, IAutorizacionService autorizacion)

        _userRepo = userRepo;

        if (usuarioObjetivo.EsAdmin)
        {
            throw new AplicationException("No se pueden modificar los permisos de un administrador.");
        }

        usuarioObjetivo.CambiarPermisos(req.NuevosPermisos);

        _userRepo.Modificar(usuarioObjetivo);
        _uow.Guardar();

        return new CambiarPermisosResponse(usuarioObjetivo.Id, usuarioObjetivo.Nombre, usuarioObjetivo.Permisos);
    }

  • Doble Capa de Verificación en Casos de Uso: Este caso de uso aplica políticas de seguridad complejas que no pueden automatizarse con un simple atributo de rol:
    • Verificación del Solicitante: Carga al usuario que inició la petición (idUsuarioSolicitante) y comprueba explícitamente si su bandera EsAdmin es verdadera. Si no lo es, cancela la ejecución mediante una AutorizacionException, evitando elevaciones de privilegios no autorizadas.
    • Protección de Administradores: Carga al usuario objetivo a modificar y verifica si es un administrador. Esto actúa como una protección de seguridad interna (invariante de aplicación).
  • Mutación a Través del Dominio: En vez de manipular directamente la base de datos o asignar una nueva lista directamente al modelo, invoca al método de dominio usuarioObjetivo.CambiarPermisos(req.NuevosPermisos) y luego persiste el estado. 4. Detalle de Clases: Capa de Infraestructura (SGE.Infraestructura)

La capa de infraestructura implementa las interfaces y provee el soporte técnico para las capas internas.

Fundamentos Teóricos de la Capa de Infraestructura

La capa de Infraestructura (implementada en el proyecto SGE.Infraestructura) es la encargada de dar soporte técnico a las reglas lógicas del negocio. Implementa las interfaces (puertos) definidas por las capas internas de Dominio y Aplicación, encargándose de la comunicación física con bases de datos relacionales, servicios de cifrado, archivos del sistema o redes. Sus pilares fundamentales son:

1. Mapeo Relacional de Objetos (ORM) y EF Core: El ORM (en nuestro caso, Entity Framework Core) actúa como un puente de traducción bidireccional entre el paradigma orientado a objetos (clases, herencia, encapsulamiento) y el paradigma relacional de SQL (tablas, columnas, claves foráneas). EF Core nos permite recuperar registros en base de datos e hidratar las clases de negocio automáticamente.

2. Conversores de Valor (Value Conversions): Dado que los motores relacionales sencillos (como SQLite) no comprenden de forma nativa los Value Objects del dominio (como Caratula o Contenido), la infraestructura utiliza la API fluida de EF Core (HasConversion) para aplanar estos objetos a cadenas primitivas de texto antes de guardarlos, y reconstruirlos mediante sus constructores de dominio al recuperarlos. Esto nos permite mantener un dominio puro y rico sin comprometer la sencillez técnica de la persistencia.

3. Patrones Repositorio y Unidad de Trabajo (Unit of Work): El *Patrón Repositorio* encapsula las consultas y escrituras de datos tras una interfaz en memoria, abstrayendo a la aplicación de los comandos SQL o llamadas al ORM. El *Patrón Unidad de Trabajo* asegura que todas las operaciones y cambios sobre múltiples repositorios ocurran dentro de una transacción de base de datos única y atómica. Si falla un cambio, toda la transacción se descarta, previniendo estados inconsistentes de la base de datos (por ejemplo, guardar un trámite pero que falle la actualización del expediente).

4. Servicios Externos de Criptografía e Identidad: Los mecanismos de seguridad (generación de JSON Web Tokens con algoritmos simétricos HMAC-SHA256, validación de firmas digitales y hashing de contraseñas de usuarios) son detalles técnicos de bajo nivel. Por lo tanto, se implementan en esta capa utilizando librerías específicas del sistema operativo o framework, exponiéndolas a través de contratos abstractos (como ITokenProvider) para evitar contaminar la capa de aplicación con librerías externas.

Explicación detallada del bloque (Mapeo Relacional de Objetos - ORM):
  • El DbContext como intermediario relacional: La clase heredada de DbContext de Entity Framework Core representa la sesión de trabajo con la base de datos SQLite y expone las tablas a través de propiedades de tipo DbSet<T>.
  • Mapeo de Value Objects Complejos mediante HasConversion (Fluent API): La base de datos SQLite solo soporta tipos nativos simples (enteros, flotantes, texto, booleanos y blobs). Para persistir los Objetos de Valor Caratula y Contenido en formato de texto plano en SQLite, configuramos HasConversion() en el constructor del modelo. Esto le enseña a EF Core a ejecutar una serialización implícita: al escribir, extrae la propiedad string Valor; al leer, reconstruye el objeto instanciando un nuevo record new Caratula(valor). Esto nos permite disfrutar de las validaciones y del encapsulamiento de DDD a nivel de C# sin alterar el esquema relacional de base de datos.

Esto nos ahorra tener que crear tablas asociativas intermedias de muchos a muchos y realizar costosas consultas JOIN solo para guardar la lista de permisos de un usuario.

Proveedor de JWT: ProveedorTokenJwt.cs

Se encarga de armar y firmar criptográficamente el token JWT a partir de los datos y permisos de un usuario autenticado. 

public class ProveedorTokenJwt : ITokenProvider
{
    private readonly string _claveSecreta;

    public ProveedorTokenJwt(string claveSecreta)
    {
        _claveSecreta = claveSecreta;
    }

    public string GenerarToken(Usuario user)
    {
        var manejadorToken = new JwtSecurityTokenHandler();
        var claveEnBytes = Encoding.UTF8.GetBytes(_claveSecreta);

        var reclamos = new List<Claim>
        {
            new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
            new Claim(ClaimTypes.Name, user.Nombre),
            new Claim(ClaimTypes.Email, user.Email),
            new Claim("esAdmin", user.EsAdmin.ToString().ToLower())
        };

        if (!user.EsAdmin)
        {
            foreach (var permiso in user.Permisos)
            {
                reclamos.Add(new Claim("permiso", permiso.ToString()));
            }
        }

        var descriptorToken = new SecurityTokenDescriptor
        {
            Subject = new ClaimsIdentity(reclamos),
            SigningCredentials = new SigningCredentials(
                new SymmetricSecurityKey(claveEnBytes),
                SecurityAlgorithms.HmacSha256Signature
            )
        };

        var token = manejadorToken.CreateToken(descriptorToken);
        return manejadorToken.WriteToken(token);
    }
}
Explicación detallada del bloque (Generación de JSON Web Tokens):
  • Estructura de un JWT (Claims / Reclamos): Un token JWT es un estándar abierto (RFC 7519) que define una forma compacta y autónoma para transmitir información de seguridad de forma segura. Los reclamos (claims) son piezas de información asociadas al usuario: su ID, nombre, email y un flag de administración. Para los usuarios que no son administradores globales, se añaden múltiples claims con la clave "permiso", facilitando que el middleware de ASP.NET Core los lea de forma directa en cada petición HTTP sin necesidad de volver a consultar a la base de datos SQLite.
  • Firma Digital y Clave Simétrica: El descriptor del token firma el payload utilizando una clave secreta codificada en bytes y el algoritmo criptográfico HmacSha256Signature. Esto produce una firma digital que se concatena al final del token. Si un atacante altera los permisos de usuario dentro del token JWT para intentar elevar privilegios en el cliente, la firma del token no coincidirá con el contenido modificado y el servidor rechazará la petición automáticamente en la etapa de middleware.

Fundamentos Teóricos de ASP.NET Core Web API

La capa de Presentación (implementada en el proyecto SGE.WebApi) constituye la frontera del sistema. Su propósito fundamental es exponer los servicios del negocio al mundo exterior mediante una API web HTTP, actuando como un adaptador de entrada (siguiendo los principios de la Arquitectura Hexagonal y la Arquitectura Limpia). A continuación se analizan sus componentes y mecanismos clave:

1. Arquitectura REST (Representational State Transfer): La Web API está construida sobre los principios de REST, lo que implica una comunicación cliente-servidor sin estado (stateless). Cada petición HTTP debe contener toda la información necesaria para ser procesada. La API utiliza Endpoints basados en URIs que identifican recursos (por ejemplo, /api/expedientes), verbos HTTP estandarizados para denotar intenciones (GET para lectura, POST para creación, PUT/PATCH para modificación y DELETE para eliminación) y códigos de estado HTTP semánticos (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Internal Server Error) para comunicar el resultado de manera uniforme a los clientes.

2. El Bootstrap y el Contenedor de Inversión de Control (IoC): El archivo Program.cs funciona como el punto de entrada de la aplicación (bootstrap). En él se configuran e inicializan los servicios que componen la infraestructura técnica y del negocio. ASP.NET Core incluye un contenedor de dependencias nativo. En la sección de servicios (builder.Services), se registran los componentes del sistema indicando su ciclo de vida (Lifetime):

  • Transient: Se crea una nueva instancia cada vez que se solicita el servicio. Adecuado para componentes livianos y sin estado.
  • Scoped: Se crea una única instancia por cada petición HTTP. Todos los componentes inyectados dentro de una misma solicitud HTTP comparten esta instancia. Es el ciclo de vida crítico para el SGEContext y los Repositorios, ya que asegura que todas las operaciones de acceso a datos de una petición utilicen la misma conexión y sesión relacional.
  • Singleton: Se crea una única instancia para toda la vida útil de la aplicación web. Se comparte entre todas las llamadas HTTP y todos los hilos, siendo ideal para proveedores de cifrado o servicios inmutables de configuración global.

3. El Pipeline de Middleware (Ciclo de Vida de una Petición): El procesamiento de solicitudes en ASP.NET Core se basa en un pipeline de middlewares dispuestos en forma de cebolla. Un Middleware es un componente de software intermedio que intercepta la solicitud y la respuesta. El orden de registro de los middlewares en Program.cs es fundamental porque determina su ejecución secuencial:

  • Middleware de Excepciones: Registrado al principio del pipeline para capturar cualquier error lanzado por middlewares subsecuentes o controladores.
  • Middleware de Autenticación (UseAuthentication): Examina la cabecera HTTP Authorization, valida la firma del token JWT y carga la identidad del usuario en el contexto de la petición (HttpContext.User).
  • Middleware de Autorización (UseAuthorization): Evalúa las políticas de acceso y comprueba si la identidad autenticada posee los privilegios requeridos para ejecutar el recurso.
  • Middleware de Enrutamiento y Controladores (MapControllers): Finalmente, dirige la llamada al controlador y acción correspondiente si las capas anteriores autorizaron el paso.

4. Controladores Delgados (Thin Controllers) y Model Binding: Los controladores heredan de ControllerBase y están anotados con [ApiController]. Este atributo activa la validación automática de DTOs de entrada y el enlace de datos (Model Binding), que traduce el cuerpo JSON de la petición HTTP directamente a objetos fuertemente tipados en C#. Siguiendo las buenas prácticas arquitectónicas, los controladores se mantienen "delgados" (thin): no contienen lógica de negocio ni de persistencia. Su única tarea es recibir los datos validados por el model binder, extraer la identidad del usuario del contexto de seguridad, delegar la ejecución real a los Casos de Uso de la capa de Aplicación y retornar el resultado formateado en una respuesta HTTP adecuada.

Middleware: ManejadorGlobalExcepcionesMiddleware.cs

Intercepta el pipeline de peticiones de ASP.NET Core capturando excepciones del sistema y devolviendo respuestas uniformes en formato JSON. 

public sealed class ManejadorGlobalExcepcionesMiddleware
{
    private readonly RequestDelegate _siguiente;
    private readonly ILogger<ManejadorGlobalExcepcionesMiddleware> _logger;

    public ManejadorGlobalExcepcionesMiddleware(RequestDelegate siguiente, ILogger<ManejadorGlobalExcepcionesMiddleware> logger)
    {
        _siguiente = siguiente;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext contexto)
    {
        try
        {
            await _siguiente(contexto);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Ocurrió una excepción no controlada al procesar la solicitud.");

            var (codigoEstado, titulo) = MapearExcepcion(ex);

            contexto.Response.StatusCode = codigoEstado;
            contexto.Response.ContentType = "application/json";

            var respuesta = new ProblemDetails
            {
                Status = codigoEstado,
                Title = titulo,
                Detail = ex.Message,
                Instance = contexto.Request.Path
            };

            await contexto.Response.WriteAsJsonAsync(respuesta);
        }
    }

    private static (int CodigoEstado, string Titulo) MapearExcepcion(Exception ex)
    {
        return ex switch
        {
            AutorizacionException => ((int)HttpStatusCode.Forbidden, "Error de autorización"),
            UnauthorizedAccessException => ((int)HttpStatusCode.Unauthorized, "No autorizado"),
            AplicationException when ex.Message.Contains("no existe", StringComparison.OrdinalIgnoreCase) || 
                                     ex.Message.Contains("no encontrado", StringComparison.OrdinalIgnoreCase)
                => ((int)HttpStatusCode.NotFound, "Recurso no encontrado"),
            AplicationException => ((int)HttpStatusCode.BadRequest, "Error de aplicación"),
            DomainException => ((int)HttpStatusCode.BadRequest, "Error de dominio"),
            RepositoryException => ((int)HttpStatusCode.NotFound, "Recurso no encontrado"),
            _ => ((int)HttpStatusCode.InternalServerError, "Error inesperado")
        };
    }
}
Explicación detallada del bloque (Middleware de Manejo Global de Errores):
  • Flujo del Pipeline de ASP.NET Core: Un middleware es un componente de software que se ensambla en el pipeline (tubería) de la aplicación para gestionar solicitudes y respuestas HTTP. Al colocar este middleware al principio del pipeline, envolvemos toda la ejecución de la API en un gran bloque try-catch mediante await _siguiente(contexto). Si cualquier controlador, caso de uso o entidad arroja un error imprevisto, la petición retrocede hasta este middleware, evitando que el servidor devuelva errores crudos de .NET o pantallas amarillas de error.
  • Mapeo Semántico de Códigos HTTP: El método MapearExcepcion() traduce las excepciones lógicas y de negocio a códigos de estado HTTP estándar:
    • AutorizacionException se traduce al código 403 Forbidden (Acceso prohibido).
    • UnauthorizedAccessException se traduce al código 401 Unauthorized (No autenticado).
    • Excepciones de dominio o aplicación (DomainException o AplicationException) se traducen a 400 BadRequest (Petición incorrecta).
    • Excepciones no controladas o genéricas del sistema se traducen a 500 InternalServerError, logueando el error con LogError para que el equipo de desarrollo pueda revisarlo.
  • Estandarización bajo Problem Details (RFC 7807): En lugar de retornar un texto simple de error, formatea la respuesta en un JSON estructurado bajo el estándar internacional RFC 7807 (Problem Details for HTTP APIs). Esto proporciona metadatos consistentes sobre el error (como el status, el título descriptivo, el detalle del error y la ruta exacta donde ocurrió) para que los clientes web o frontend los procesen de forma consistente.

public sealed class FiltroAutorizacion : IDocumentFilter
{
    public void Apply(OpenApiDocument documento, DocumentFilterContext contexto)
    {
        foreach (var apiDescription in contexto.ApiDescriptions)
        {
            var metadatosDelEndpoint = apiDescription.ActionDescriptor.EndpointMetadata;
            var tieneAutorizacion = metadatosDelEndpoint.OfType<AuthorizeAttribute>().Any();
            var permiteAnonimo = metadatosDelEndpoint.OfType<AllowAnonymousAttribute>().Any();

            if (!tieneAutorizacion || permiteAnonimo) continue;

            if (string.IsNullOrWhiteSpace(apiDescription.RelativePath) || string.IsNullOrWhiteSpace(apiDescription.HttpMethod))
            {
                continue;
            }

            var ruta = "/" + apiDescription.RelativePath.Split('?')[0].TrimEnd('/');
            if (ruta == "//") ruta = "/";

            if (!documento.Paths.TryGetValue(ruta, out var pathItem)) continue;

            if (!pathItem.Operations.TryGetValue(new System.Net.Http.HttpMethod(apiDescription.HttpMethod), out var operation))
            {
                continue;
            }

            operation.Security ??= [];

            var yaMarcado = operation.Security.Any(requisito =>
                requisito.Keys.OfType<OpenApiSecuritySchemeReference>().Any(referencia =>
                    string.Equals(referencia.Reference?.Id, "Bearer", StringComparison.Ordinal)));

            if (yaMarcado) continue;

            operation.Security.Add(new OpenApiSecurityRequirement
            {
                [new OpenApiSecuritySchemeReference("Bearer", documento)] = new List<string>()
            });
        }
    }
}
Explicación detallada del bloque (Metadatos Dinámicos en Swagger UI):

    private Guid ObtenerIdUsuarioDelToken()
    {
        var claim = User.FindFirst(ClaimTypes.NameIdentifier);
        if (claim == null)
        {
            throw new UnauthorizedAccessException("No se pudo obtener el ID del usuario del token.");
        }
        return Guid.Parse(claim.Value);
    }

    [HttpPost]
    public IActionResult Agregar([FromBody] AgregarExpedienteRequest request)
    {
        var idUsuario = ObtenerIdUsuarioDelToken();
        var response = _agregarExpedienteUseCase.Ejecutar(request, idUsuario);
        return Ok(response);
    }

Explicación detallada del bloque (Controladores REST y Extracción de Contexto):
  • Atributos Declarativos de ASP.NET Core: El atributo [ApiController] habilita comportamientos específicos de API REST (como validaciones automáticas de modelos de entrada y enrutamiento inteligente). El atributo [Authorize] a nivel de clase actúa como un guardián: garantiza que ningún método (como Agregar()) pueda ser ejecutado a menos que el cliente envíe una cabecera con un token JWT firmado y validado por el middleware de seguridad.
  • Extracción de Identidad del Token JWT (Firma Digital): El método helper ObtenerIdUsuarioDelToken() lee la propiedad interna User (que representa al Principal de seguridad de la petición actual). Busca el claim ClaimTypes.NameIdentifier, extrae su valor en string y lo parsea a un tipo GUID. Este enfoque es altamente seguro ya que la identidad del usuario proviene del token firmado criptográficamente, impidiendo que un cliente malicioso envíe peticiones suplantando el ID de otro usuario en el cuerpo de la solicitud JSON.

6. Guía de Estudio y Defensa del Proyecto (Preguntas Frecuentes)

Esta sección funciona como una guía rápida para el examen o defensa oral del proyecto. Contiene las preguntas teóricas y técnicas más frecuentes de los evaluadores, junto con sus fundamentos arquitectónicos explicados conceptualmente:

P1: ¿Por qué eligieron una Arquitectura Limpia/Hexagonal y no una tradicional de 3 Capas?

Respuesta: En una arquitectura tradicional de 3 capas (Presentación -> Negocio -> Acceso a Datos), la lógica de negocio depende directamente de los detalles de infraestructura. Si cambia la base de datos o el ORM, se debe modificar y recompilar todo el sistema.

Al utilizar Arquitectura Limpia, aplicamos el principio de Inversión de Dependencias (D de SOLID). El Dominio (las reglas puras del negocio) y la Aplicación (los casos de uso) están en el centro del sistema y no conocen los detalles técnicos externos. Definen interfaces abstractas (puertos como IExpedienteRepository). La capa de Infraestructura implementa estos puertos (adaptadores). Esto provee:

  • Desacoplamiento total: Se puede cambiar SQLite por PostgreSQL o SQL Server modificando únicamente los adaptadores de infraestructura, sin alterar el código comercial.
  • Testabilidad independiente: Permite probar unitariamente la lógica comercial inyectando repositorios simulados (mocks) en memoria, sin necesidad de conectarse a una base de datos física real.
P2: ¿Cuál es la diferencia conceptual entre una Entidad, un Value Object y un DTO?

Respuesta: Cada uno posee una responsabilidad única en la arquitectura:

  • Entidad (ej. Expediente, Usuario): Posee una identidad única mutable (`Guid Id`) y un ciclo de vida con estados. Dos entidades son idénticas si comparten el mismo identificador único, aunque sus propiedades internas difieran en el tiempo.
  • Value Object (ej. Caratula, Contenido): Carece de identidad. Se define puramente por el valor de sus propiedades y es inmutable. Si cambia, se crea una nueva instancia completa. La comparación se hace por igualdad estructural de sus campos y no por puntero. Se utiliza para auto-validar lógica comercial primitiva.
  • DTO (Data Transfer Object): Estructura plana de datos (sin comportamiento) diseñada únicamente para transferir información a través de los límites del sistema (desde el cliente HTTP hacia la API y viceversa). Evita exponer las entidades internas del dominio directo a los clientes externos.
P3: ¿Cómo funciona el Patrón Unidad de Trabajo (Unit of Work) y cuál es su beneficio?

Respuesta: El patrón IUnidadDeTrabajo coordina múltiples llamadas a repositorios bajo una única transacción de base de datos lógica.

Si no usáramos Unidad de Trabajo y cada repositorio realizara su propio guardado de cambios a base de datos, un error en la mitad de un caso de uso (como registrar un trámite con éxito pero fallar al actualizar el estado del expediente asociado) dejaría la base de datos en un estado corrupto e inconsistente. Al agruparlas bajo la Unidad de Trabajo, los cambios quedan guardados en el Change Tracker de EF Core y se aplican de manera atómica (todo o nada) en una transacción transaccional.

P4: ¿Por qué implementaron una Autorización basada en Permisos en lugar de Roles?

Respuesta: La autorización basada en Roles (ej: [Authorize(Roles = "Admin")]) es rígida. Si mañana el negocio requiere un nuevo rol (ej. "OperadorJunior") con un subconjunto de acciones de otro rol, se requeriría modificar el código C# en todos los controladores donde se definieron los accesos.

Con la autorización basada en Permisos granulares (ej: ExpedienteAlta, TramiteAlta), protegemos cada endpoint individualmente con el permiso correspondiente. Los usuarios tienen asignada una lista de permisos específicos. La creación de nuevos roles o el ajuste de privilegios de un usuario se realiza dinámicamente desde la persistencia o asignándolos en el token JWT, sin requerir cambios ni recompilaciones en el código de la API.

P5: ¿Cómo mantienen la pureza del Dominio si utilizan Entity Framework Core como ORM?

Respuesta: Para evitar acoplar la capa comercial con infraestructura, las entidades de dominio no utilizan atributos decorativos del ORM (como [Key], [Table] o [Required]).

Toda la configuración del mapeo de tablas, llaves foráneas y tipos relacionales se realiza en la capa de Infraestructura (dentro de SGEContext.cs) utilizando la API Fluida (Fluent API). Asimismo, los Value Objects complejos se mapean a tipos relacionales primitivos mediante conversores de valor (HasConversion). De este modo, el dominio se mantiene como código C# puro (POCO) completamente ajeno a los mecanismos relacionales físicos.

P6: ¿Cómo interactúan el Middleware de Seguridad y el Filtro de Autorización?

Respuesta: El proceso consta de dos fases secuenciales:

  1. Autenticación (Middleware): Cuando llega la petición HTTP, el middleware de ASP.NET Core intercepta la cabecera Authorization, valida la firma criptográfica del JWT y mapea los claims de seguridad (como los permisos del usuario) en el principal del contexto (HttpContext.User).
  2. Autorización (Filtro): El filtro FiltroAutorizacion intercepta la llamada justo antes de llegar al controlador, recupera el permiso requerido por la acción del controlador y verifica si el usuario autenticado tiene ese permiso en sus claims. Si no lo tiene, interrumpe el flujo y devuelve un error 403 Forbidden sin llegar a procesar el controlador.
P7: ¿Cómo se configuran los Endpoints en la Web API y cómo se mapean los parámetros (Model Binding)?

Respuesta: Los endpoints se exponen a través de controladores REST que heredan de ControllerBase. Su configuración y el mapeo de datos se realiza mediante atributos declarativos de ASP.NET Core:

  • [ApiController]: Activa comportamientos orientados a APIs, como la validación automática del estado del modelo (si el JSON de entrada no cumple con las anotaciones, devuelve un 400 Bad Request automáticamente) e infiere el origen de los parámetros.
  • [Route("api/[controller]")]: Define la plantilla de URL base para acceder a los endpoints del controlador (por ejemplo, api/expedientes).
  • Verbos HTTP ([HttpPost], [HttpGet("{id}")], etc.): Determinan el método HTTP requerido para la acción. Al usar llaves en la ruta (como "{id}"), se define una variable de ruta dinámica.
  • Mapeo de Datos (Model Binding):
    • [FromBody]: Le indica al framework que debe deserializar el cuerpo JSON de la petición HTTP directamente a una clase DTO de entrada (ej: AgregarExpedienteRequest).
    • [FromRoute]: Indica que el parámetro debe ser extraído del segmento dinámico de la URL (ej: el Guid id en la ruta /api/expedientes/{id}).
    • Seguridad de Contexto: La identidad del usuario (su ID de cuenta) nunca se pasa en el JSON del cuerpo por motivos de seguridad; se extrae en el servidor leyendo el claim del token JWT autenticado (User.FindFirst(ClaimTypes.NameIdentifier)).
P8: ¿Cómo defender la ubicación de un archivo si sale al azar en una "bolilla" de examen?

Respuesta: Si el tribunal elige un archivo al azar de la solución, la clave para defenderlo es clasificarlo en su capa correspondiente y explicar su responsabilidad en la arquitectura:

  • Capa de Dominio (SGE.Dominio) — El Corazón del Negocio:
    • Archivos ejemplo: Expediente.cs, Caratula.cs, EstadoExpediente.cs, DomainException.cs.
    • Defensa: "Este archivo está en el Dominio porque representa las reglas esenciales e invariantes del negocio. Es código C# puro (POCO), no tiene dependencias de bases de datos, APIs ni librerías externas. Si las normas del sistema de gestión de expedientes cambian en la vida real, se modifica en esta capa".
  • Capa de Aplicación (SGE.Aplicacion) — Los Orquestadores de Casos de Uso:
    • Archivos ejemplo: AgregarExpedienteUseCase.cs, IExpedienteRepository.cs, AgregarExpedienteRequest.cs.
    • Defensa: "Pertenece a la capa de Aplicación porque coordina el flujo de los datos del sistema. Los archivos UseCase implementan las intenciones del usuario llamando al dominio y persistiendo a través de interfaces. Aquí definimos las interfaces (puertos) porque la Aplicación dicta qué necesita para operar, pero delega el cómo se hace a la infraestructura".
  • Capa de Infraestructura (SGE.Infraestructura) — Los Detalles Tecnológicos:
    • Archivos ejemplo: SGEContext.cs, ExpedienteRepository.cs, ProveedorTokenJwt.cs, SGESqlite.cs.
    • Defensa: "Este archivo es de Infraestructura porque contiene la implementación tecnológica concreta (los adaptadores). Aquí nos acoplamos a paquetes externos (como Entity Framework Core para SQLite o JwtBearer para seguridad). Es la capa encargada de interactuar con el disco duro, la base de datos física o los algoritmos de encriptación".
  • Capa de Presentación (SGE.WebApi) — El Punto de Entrada Técnico:
    • Archivos ejemplo: ExpedientesController.cs, Program.cs, ManejadorGlobalExcepcionesMiddleware.cs, FiltroAutorizacion.cs.
    • Defensa: "Está en la capa de Presentación porque actúa como el punto de inicio de la aplicación para el cliente externo. Configura el pipeline HTTP de ASP.NET Core, realiza la inyección de dependencias, valida el token JWT de entrada y rutea las peticiones REST hacia la capa de aplicación".
